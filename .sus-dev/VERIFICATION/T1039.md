# T1039 — hover and checked are driven; a native tick is not judged

**Task:** the fourth DOM-representable state. Issue #21 R6 left pressed/disabled measured; hover is a real
DOM state, and `:checked` is too — but only where the appearance is custom.
**Branch / base:** `chore/continuation-reconciliation` after `0e349a4` (T1038).

## Verdict

**Pass.** Four states are now driven (hover, pressed, disabled, checked) and two exclusions are stated
rather than papered over.

| State | Driven how | Measured |
| --- | --- | --- |
| hover | pointer moves onto the control | changed computed properties vs idle |
| pressed | pointer down, **compared with hover** | changed properties vs hover |
| disabled | the control's own attribute, set then restored | changed properties vs idle |
| checked | `:checked` flipped for a custom-appearance checkbox/radio | changed properties vs idle |
| checked (native) | **not judged** | reported as skipped, with the reason |
| loading / success / error | **not driven** | named in every report |

## Three defects this task found in T1038's own probe

1. **The press was measuring hover.** Press was compared with idle, so a control with a hover style but no
   `:active` difference scored a non-zero "press" delta and would have passed. It is now compared with the
   *hover* snapshot. `fixtures/bestpractice/states-flat` keeps its hover style and still reports
   `pressed 0/10` — the test would fail if the comparison regressed.
2. **Pressing a checkbox clicked it.** `mouse.down`/`up` on a checkbox toggles it, which reverted the state
   the checked probe was about to measure (measured: `checked 0` for a control that visibly draws it). The
   press is now skipped for toggles, with `pressSkippedReason` naming why.
3. **`:checked` does not re-resolve in the task that flips it.** Flipping the property and reading computed
   style in one `evaluate` returned the *old* background, hiding a real checked state. The flip, a frame,
   and the read are now three steps.

## Native controls are not claimed broken

A native checkbox paints its tick outside computed style, so a style delta of zero says nothing about it.
Reporting "checked state looks unchecked" there would be a false finding, so the probe records
`checkedSkippedReason: 'its appearance is native, …'` and the check detail prints `checked not judged`.
`fixtures/bestpractice/states-checked` holds all three cases: a custom checkbox that draws its state, a
custom one that deliberately draws nothing, and a native one that is not judged.

## Check status cannot drift from the findings

The status was recomputed from a second, hand-written predicate — which missed the new findings and said
**pass** while the report carried two component-state findings. It is now read from the findings the check
just pushed, so `pass` means "no component-state finding", by construction.

## Proof

`packages/eval-core/tests/component-states.test.ts` — 7 tests, green:

- hover delta > 0 on both fixtures; `pressSkippedReason` null for a button;
- the flat fixture reports `pressed 0` **and** a real hover delta (the press-vs-hover comparison);
- the checked fixture: custom `checked > 0`, flat `checked == 0`, native `checked === null` plus a
  skip reason containing `native`;
- a deep audit of the checked fixture fails with `Checked state looks unchecked`, `observed 0`, and does
  **not** name the honest control;
- a page with no control stays `not-run` with the reason.

## Stated limits

- Three controls per route, document order.
- Only a custom appearance is judged for `checked`; a native one stays unjudged by design.
- The measurement is presence of a style change, not quality.
