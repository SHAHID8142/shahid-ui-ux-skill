# T1032 — one entry point: `sus <command>` (issue #21 R3)

**Task:** issue #21 R3: the root `package.json` had no `bin`; using SUS meant knowing
`./packages/{adapters,eval-core,scanners}/dist/cli.js`, or three `pnpm exec sus-…` names that appear
nowhere a user starts reading.
**Approval:** D32 issue triage inside D28; follows the owner's `go ahead` on the R-series.
**Branch / base:** `chore/continuation-reconciliation` at `4cc55b1`.

## Verdict

**Pass.** `pnpm exec sus <command>` (also `node bin/sus.mjs …`) runs the CLI that already owns the
command, with arguments and exit codes unchanged. It adds no behaviour and no new exit codes.

## The map is the CLIs' own map

| Owner | Commands |
| --- | --- |
| eval-core | `audit`, `bestpractice`, `capture`, `evidence`, `score`, `budget` |
| scanners | `scan` (a path, not a subcommand — so no command word is passed) |
| adapters | `route`, `load`, `precedence`, `capabilities`, `status` |

A wrapper's real risk is drift — advertising a command the CLIs dropped, or missing one they added —
so `packages/eval-core/tests/cli-entry.test.ts` spawns each CLI, parses its **own** usage line, and
compares the sets in both directions. Adding a command to a CLI without wiring it here fails the test,
and so does the reverse.

## Behaviour

| Input | Result |
| --- | --- |
| `sus` | usage on stderr, exit 2 (a missing command is a usage error, like every SUS CLI) |
| `sus --help` | the map on stdout, exit 0 |
| `sus auditt` | `unknown command "auditt"` + the map, exit 2 — no "did you mean", because that would be a guess |
| `sus audit --bogus` | the eval-core usage error, exit 2 (unchanged) |
| `sus audit --help` | the eval-core audit help, exit 0 (the owner answers, not the wrapper) |
| `sus scan <file>` | `0 finding(s)`, exit 0 |
| `sus capabilities` | the capability matrix, exit 0 |
| `sus <cmd>` before `pnpm build` | `error: <owner> is not built (…)\nrun: pnpm build`, exit 2 |

## Second defect found while wiring it

`sus audit --bogus` printed a Node-internal `ERR_PARSE_ARGS_UNKNOWN_OPTION` stack fragment and exited
**0** — the audit command had been left on raw `parseArgs` when the other four were moved to
`parseOrFail` (issue #21 §3.2 fixed only those). It is now a one-line usage error with exit 2.

Moving it exposed why: `OptionValue<T>` checked `type: 'string'` before `multiple: true`, so
`--authorize` (a repeatable string) was typed as a bare `string` and would have been read wrongly.
The conditional order is fixed and documented.

## Proof

`packages/eval-core/tests/cli-entry.test.ts` — 5 tests, green:

1. the map equals the commands each CLI advertises (both directions);
2. no command → exit 2 with usage; `--help` → exit 0 with exactly the map;
3. unknown command → exit 2, no guessed replacement;
4. pass-through: `audit --bogus` → 2, `scan <clean file>` → 0, `audit --help` → 0 with the owner's text;
5. `plan()` keeps the command word only for the owners that take one.

## Stated limits

- Nothing is published: `bin` is wired for in-repo use (`pnpm exec sus`), and publication stays an
  owner decision (T1005). No claim is made that `npx sus` works from outside this repository.
- The wrapper does not translate flags: a SUS exit code is whatever the owning CLI returns.
- `docs/QUICKSTART.md` and `docs/BESTPRACTICE_COMMAND.md` now show `sus …`; the long forms are kept
  because they work without the wrapper.
