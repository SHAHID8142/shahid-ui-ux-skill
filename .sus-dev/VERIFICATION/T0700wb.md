## What the experiment does (no mocks)

For each stack, on a disposable copy of the real fixture with its own
`node_modules` linked:

1. stamp every renderable source with `stampSource` (T0700wa);
2. really build it — `next build` (prerenders `.next/server/app/index.html`) or
   `astro build`;
3. serve that built HTML and select the anchor with a real browser
   (`resolveSelection`, Playwright);
4. resolve the anchor to one source owner (`resolveOwner`);
5. open an isolated `PreviewSession`, approve it, and apply through
   `ApplyEngine` with the stack's own build as the verifier;
6. assert the written bytes equal the approved postimage, the stack still
   builds, undo restores the exact preimage, and a second undo is refused;
7. run the denials: page-derived provenance, and a retry after consumption
   (exactly one edit on disk).

## The blocker (found here, not guessed)

`src/editor.ts` parses TSX only. On an `.astro` source it returns
`unparseable-source` and the file stays **byte-identical** — correct fail-closed
behaviour, and the test asserts exactly that. But it means there is no Astro edit
path at all, so the Astro stack cannot complete the chain.

- **Created:** T0700wc — Astro source editing in the safe-write editor, with
  acceptance for all five operations, anchor preservation, frontmatter/script
  boundary safety, and re-running this suite's Astro half.
- **T0700wb stays `blocked`** until T0700wc lands. It is not marked done, and
  the parent T0700w stays open.

## Harness bugs found and fixed while building this (worth knowing)

- `VerificationResult` is `{ status: 'pass' | 'fail' }`, not `{ ok }` — the
  first version silently reverted every successful apply. The receipt said
  `reverted: verification failed: next build succeeded`, which is how it was
  caught; the engine was right, the harness was wrong.
- The apply path checks the approval *before* the capability, so a retry after a
  successful write dies as `stale-approval` rather than `capability-replayed`.
  Both are refusals and both leave the tree with exactly one edit; the test now
  asserts the guarantee rather than an internal ordering.
- `VisualIntentData` requires `constraints` and `unknowns` — an intent without
  them is not a valid intent and the preview refuses.

## Honest limitations

- The Astro apply/undo legs are unproven by construction (no editor). They are
  not claimed.
- "Zero harmful wrong-owner writes" is observed over the labelled labels tested
  here (section anchors, map instances, headings, unknown/ambiguous/computed
  ownership); it is evidence for these shapes, not a proof for every markup
  pattern.
- Selection is proven against the **prerendered** HTML of each stack, which is
  what these fixtures serve. A fully client-side hydrated app renders the same
  anchors but was not exercised here.
