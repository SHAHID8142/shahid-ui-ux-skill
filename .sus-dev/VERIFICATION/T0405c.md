## The two acceptance items, concretely

**Payment states** are a closed vocabulary stated as a rule: `idle`, `authorising`,
`authorised`, `captured`, `declined`, `requires-action`, `unknown` — each with its own
copy, and `unknown` is a *state*, not an error. That last distinction is the one that
matters commercially: a timeout is not a decline, and telling a shopper their card failed
when the outcome is unknown causes them to pay twice.

**Duplicate-submit checklist** (all five required, per the rule text): the control disables
on press; the guard lives in the handler *as well as* the UI (because a disabled attribute
is not a guard — a double `click` can queue before the disable paints); the request carries
an idempotency key; a retry reuses the same key; a resumed session re-checks order state
before re-submitting. A test asserts each guard phrase is present, so the checklist cannot
be trimmed away later without failing the suite.

## The other three components

- **product-grid** — comparability is the rule: same attributes in the same order, one
  aspect ratio per grid, reserved space so nothing reflows. A card missing price or stock
  says so in text rather than showing a placeholder figure a shopper could read as a price.
- **pdp** — "changing a variant updates price, availability and image together or says
  which is unchanged"; a silently stale price is named as a defect. Availability wording is
  observed fact only — no invented scarcity (the taxonomy's `dark-urgency` refusal, applied).
- **cart-summary** — final vs estimated totals labelled at the point of display; quantity
  edits re-read the server value, never keeping an optimistic quantity the server rejected;
  removal is reversible for the session; checkout disabled while the cart is inconsistent,
  **with the reason stated**.
