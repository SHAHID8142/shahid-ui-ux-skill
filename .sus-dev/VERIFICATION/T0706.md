## What landed

### `diff.ts` — the two views the task's rollback names

Hand-rolled LCS line diff (no new dependency: every added package is new
supply-chain surface, and the bridge's job is to minimise that). Common
prefix/suffix trimming keeps the DP table small for the normal case (one changed
section of an otherwise identical file).

- `diffLines` → context/del/add ops in reading order.
- `buildHunks` → `@@ -a,b +c,d @@` hunks with ≤3 context lines; adjacent changes
  within `2*context` merge into one hunk.
- `unifiedDiff` → git-shaped `--- a/path` / `+++ b/path` output with a trailing
  newline (pasteable into a review).
- `splitDiff` → **row-aligned** side-by-side rows: deletions are paired with the
  additions that replace them and the shorter side is padded, so the reader
  compares corresponding lines instead of scanning two unrelated columns. That
  pairing is a direct answer to this task's stated risk ("diff readability");
  the naive column build was the alternative and it was rejected for that reason.

### `preview.ts` — the preview and the thing that must not be skippable

`PreviewSession.open(root, intent, edits)` stages preimages *and* postimages in
a `mkdtemp` workspace **outside the repo root**; the only touch on the consuming
project in the session's whole life is `readFileSync`. `propose()` returns:

- **files affected** — path, `modify|create|delete`, before/after SHA-256;
- **before/after** — additions/deletions plus unified **and** split views;
- **confidence** — carried from `intent.target.confidence`; a proposal never
  reports more certainty than the mapping that produced it;
- **responsive alternative** — derived from the intent's reflow/spatial
  constraint. When the intent captured neither, it says `not-captured` and tells
  the user the narrow result is unverified. Inventing a plausible responsive
  claim was the alternative and it is exactly the failure this product exists to
  prevent;
- **unknowns** carried forward from the intent (questions are not done work).

`requiresApproval` is a literal `true` and is not settable. Apply is **not** in
this module: `PreviewSession.approve(decision)` converts an explicit out-of-page
decision naming *this* proposal into a single-use `ApprovalGrant` bound to the
proposal's content hash, and `verifyGrant()` re-checks it against the files **as
they are now**:

| Reason | Meaning |
| --- | --- |
| `stale-base` | a target file changed after the preview — the approved diff no longer describes reality |
| `hash-mismatch` | the grant belongs to different proposal content |
| `expired` | approvals are fresh by construction (10 min TTL), never standing |
| `rejected` / `unknown-proposal` | nothing to apply against |

Approval is a data record the caller must construct, never a side effect of
rendering the preview, and never an in-page DOM event (peer finding
`mmwg0nchr-a9439f`: isolated worlds isolate JS state, not DOM events, so the
hostile page can synthesize clicks on overlay controls). T0707 consumes
`verifyGrant()` immediately before its first mutation.

Path safety fails closed and loudly: absolute paths, `../` escapes and
non-canonical paths (`./page.tsx`) are **refused**, not normalized — a
normalized path can point somewhere the user never saw.

## Honest limitations

- No HTTP preview endpoint was added. The bridge's server is a **read-only
  session surface** by design (T0701/T0703); exposing a preview route before
  T0707/T0806 land would widen the attack surface ahead of its security suite.
  The workspace + proposal objects are the contract the T0708 browser harness
  will serve.
- Intra-line (word-level) diff is not implemented; source edits proposed here
  are whole-block changes, and word diff would change no decision.
- The responsive alternative is *described from the intent*, not rendered at a
  width. Rendering it needs the same T0708 harness.
