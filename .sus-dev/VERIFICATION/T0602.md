| Finding | Fix |

## The three acceptance items

**No click duplication** — a knowledge rule plus a gate: disable on press is
necessary but not sufficient (a second `click` can queue before the disable
paints), the handler refuses a second in-flight request, and the write carries an
idempotency key reused on retry. A spinner is feedback, never a guard; that
sentence is in the reference file because it is the misconception that produces the
bug.

**Focus preserved across animated change** — focus moves because the user's intent
moved, never to follow an animation; a dialog records its trigger and returns focus
there even when the close happened mid-exit; if the trigger is gone, focus goes to
the next meaningful element and the change is announced; reduced motion must not
change the focus path. The gate requires the focus rule to exist in the playbooks
where focus actually travels (navbar, dialog, card, data table, form input).

**Motion decision record + information-preserving reduced motion** — every one of
the 16 playbooks already carries per-transition records (T0405/T0405c/T0407). The
gate now refuses an evasive reduced-motion equivalent (`none`, `disabled`, `off`),
requires a duration or an explicit immediacy for every non-`none` transition, and
refuses `cancel-restart` on any transition that reports a server outcome — the
case where a reversible animation lets the UI claim a state the server never
reached.

## Honest limitations

- Durations come from categories in the motion-token contract (fast/base/slow), and
  the band is a convention from practice — not a measured perceptual threshold. No
  claim to the contrary is made.
- The gate validates *declared* motion; it cannot see rendered motion. Proving the
  built page obeys its plan is browser-level work (T0603/T0906).
- `slow` (>240 ms) is excluded from the launch set by policy; a project needing it
  must justify it in the transition record rather than silently exceed the band.
- I corrected playbook *content* to satisfy the gate in four places. In each the
  content was genuinely weaker than the playbook claimed (a double-submit rule that
  named no idempotency key is a rule that does not survive a retry) — this was not
  the gate being "too strict".
