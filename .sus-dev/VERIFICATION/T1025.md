# T1025 — the allowlist holds per redirect hop (issue #18)

**Task:** issue #18 — `/sus audit` authorised the URL it was given and then followed redirects
wherever they pointed. An authorised server could make the audit request another origin (including a
private address) without the operator authorising it.
**Approval:** owner rule D32 (issue triage → bounded fix) inside D28 build authorisation.
**Branch / base:** `chore/continuation-reconciliation` at `665ff01`.

## Verdict

**Pass.** The initial-URL check is no longer the only check. HTTP fetches follow redirects one hop at
a time and refuse any hop off the allowlist; the audit stops (exit 2) and writes no report. Browser
phases are launched behind a local allowlisting proxy that refuses the redirect hop and any
subresource aimed at a host the operator did not authorise.

## What was actually wrong

Two independent gaps, both reproduced before the fix:

| Path | Before | Reproduction |
| --- | --- | --- |
| HTTP fetch | `fetch(url, { redirect: 'follow' })` followed a 30x to any host | local server returning `Location: http://…/audit-me` was fetched with no allowlist check |
| Browser phases | `page.goto` followed redirects inside the network stack; `page.route` is **never** called for the redirect hop | route handler logged only `http://127.0.0.1:<port>/`, then the browser resolved the external host |

The second one is the reason a route-based guard was not enough: it was measured, not assumed
(`/tmp/susmanual/dbg.mjs`: one route event, then `ERR_NAME_NOT_RESOLVED` at the external host).

## Fix

| File | Change |
| --- | --- |
| `packages/eval-core/src/audit/contract.ts` | extracted `isAuthorizedHost` / `isAuthorizedUrl` so every check uses one rule |
| `packages/eval-core/src/harness/net-guard.ts` | `followAuthorized` (manual redirects, `MAX_REDIRECT_HOPS = 5`, typed `AuthorizationRefusedError`), `guardNavigations` (route-level refusal for same-page navigations), `launchGuardedBrowser` |
| `packages/eval-core/src/harness/authorized-proxy.ts` | allowlisting proxy: plain requests and `CONNECT` tunnels are checked against the same allowlist; refusals are recorded and answered `403` |
| `packages/eval-core/src/audit/pipeline.ts` | routes fetched through `followAuthorized`; a refusal is fatal instead of a per-check `not-run`; browser phases use `launchGuardedBrowser` |
| `packages/eval-core/src/harness/capture.ts`, `src/hardening.ts` | both matrices launch through the guarded browser |
| `docs/AUDIT_COMMAND.md` | the boundary and its two stated limits |

`--proxy-bypass-list=<-loopback>` is required and set: Chromium otherwise bypasses proxies for
loopback targets, which would leave the most common audit target unguarded.

## Proof

`packages/eval-core/tests/net-guard.test.ts` — 9 tests, all green, two real servers:

| Test | Proves |
| --- | --- |
| follows a redirect inside the allowlist | same-origin 302 still works, chain recorded |
| refuses an off-allowlist hop before it is fetched | the unauthorised origin is **never requested** (fetch spy) |
| refuses a redirect into a private range address | `169.254.169.254` metadata target refused |
| refuses credential-bearing / non-http redirect | `https://user:…@host/`, `file:///etc/passwd` refused |
| refuses chains longer than the cap | loop stops at `MAX_REDIRECT_HOPS` |
| audits a loopback redirect | loopback→loopback still audited (no false refusal) |
| refuses an unauthorised redirect (real `runAudit`) | rejects with the named host **and** writes no `audit.json` |
| browser redirect hop | proxy answers `403`, refusal recorded, body is the refusal |
| authorised browser navigation | `200`, empty refusal log, page title readable |

Related suites re-run after the change: `audit`, `cli`, `hardening`, `keyboard`, `capture` — 65 tests
pass.

## Stated limits (not hidden)

- HTTPS tunnels are checked at the `CONNECT` host, not inside the tunnel: the tool constrains *which
  hosts* a page contacts, not what a response says.
- Lighthouse launches its own Chrome and is **not** proxied; it is constrained by the pre-fetch
  refusal (the origin is fetched through `followAuthorized` before Lighthouse runs).
- A server that answers the pre-flight request differently from the browser request (TOCTOU) is not
  fully prevented for the browser phases; the final-URL assertion refuses the measurement when the
  landing host is off-list.
