# T1046 — route the deep-mode Lighthouse Chrome through the authorized proxy (audit finding T1003-1)

Date: 2026-11-18 · Agent: zcode-audit · Branch chore/continuation-reconciliation

## What changed

- `packages/eval-core/src/harness/scans.ts`: `runLighthouse(url, chromePath, options?)` gains
  `options.proxyUrl`; when set, the chrome-launcher Chrome is launched with
  `--proxy-server=<proxy>` **and** `--proxy-bypass-list=<-loopback>` (without the bypass flag
  Chromium silently skips the proxy for loopback targets — the audit's main target class).
- `packages/eval-core/src/audit/pipeline.ts` (`collectScans`): the Lighthouse phase now starts its
  own `startAuthorizedProxy(authorizedHosts)` (the guarded browser's proxy is closed with the
  guarded browser, before this phase), holds it across every route, and closes it in a `finally`.
  Proxy-start failure is fail-closed: every route lands in `lighthouse.failed`
  (`no network guard: …`), which keeps the check out of `pass` — the phase never runs unguarded.
- Tests: `packages/eval-core/tests/lighthouse-guard.test.ts` (unit, mocked chrome-launcher/lighthouse:
  proxy flags present when asked, absent when not — standalone `runLighthouse` callers unchanged) and
  `net-guard.test.ts` "lighthouse phase boundary" (real Chrome, real proxy).

## Evidence (commands run at this tree)

- `pnpm --filter @sus/eval-core exec vitest run tests/lighthouse-guard.test.ts tests/net-guard.test.ts`
  → **12/12 pass** (9.07s). The real-Chrome run (7.4s) serves a loopback page embedding
  `<img src="http://blocked.invalid/leak.png">`, runs `runLighthouse(url, chrome, {proxyUrl: proxy.server})`:
  the authorized origin is measured through the proxy (`totalByteWeight > 0`), and
  `proxy.refused()` contains `blocked.invalid` — the hostile subresource was refused **and recorded**,
  where pre-fix the same request reached the host directly and `audit.json` showed nothing.
- `pnpm typecheck` → exit 0 (eval-core, studio-web, … all Done).
- Pre-fix repro (audit, 3 runs): unauthorized LAN listener received img+fetch hits from the
  unproxied chrome-launcher Chrome during `--mode deep`; `grep 192.168 audit.json` → empty.
  Post-fix the same shape cannot reach the host: the proxy refuses it and the refusal list carries it.

## Residual honesty notes

- The proxy refuses **all** unauthorized hosts for the Lighthouse Chrome (documents and
  subresources alike), which matches the policy every other phase already runs under; the
  page-level "subresources are allowed" limitation applies to the *authorized* origin's own
  resources, which flow through the proxy normally.
- Refusal surfacing in the report itself is T1052 (T1003-7), landed separately.
