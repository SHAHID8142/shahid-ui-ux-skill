# T1045 — two timeouts were measuring the machine, not the code

**Found by:** the full `pnpm verify` run after T1043/T1044. Four files failed; three passed on re-run
alone, and one passed alone in 285 s against a 420 s budget.

## Verdict

**Pass**, with the distinction stated: no code was wrong. Two waits were calibrated to a quiet machine.

| Failure | Alone | Under the full suite | Cause |
| --- | --- | --- | --- |
| `bestpractice.command.test.ts` scoped deep run | **pass, 285 s** | **timed out at 420 s** | the suite runs many Lighthouse/Chromium jobs at once |
| `a11y-budgets`, `harness` "fixture server not ready" | pass | failed | 30 s was not enough for `next start` to bind under load |
| `admin-responsive` negative control | pass | failed once | same contention |
| `lab-notice`, `bestpractice.page-scope`, `bestpractice.scoped-axe` | pass, 213 s for all 12 tests | **all timed out at 180 s** | the same cause, on a second run of the whole suite |

The second run is what stopped this being a one-off: widening two numbers had not removed the cause, it had
moved it to the next three files.

## What changed

- The deep best-practice test's timeout is **720 s**, and the comment now records the *measured* 285 s
  and the fact that the earlier 420 s budget was exceeded under parallelism — so the number is a recorded
  headroom, not a guess.
- `waitForReady` in the five fixture-server suites waits **90 s** instead of 30, and its error now says how
  long it waited: `fixture server not ready at … after 90000 ms`. A failure that says "not ready" without
  saying for how long invites exactly the guesswork this round is trying to remove.
- **The real fix: `maxWorkers: 4` in `packages/eval-core/vitest.config.mts`.** This package has twenty-odd
  files that drive a real browser, Lighthouse or `next start`; at one worker per core (ten here) they
  compete for CPU. Capping the workers keeps the suite measuring the code instead of the scheduler.
  Measured after the cap: **402 s total, 97 files + 3 skipped, 1057 tests, all green** — the same suite
  that had failed three files at 180 s each.

## Why not just widen everything

Raising a timeout hides a real failure if the test is slow for a product reason. That is why the change is
paired with a measurement rather than a bare number: the deep test passes in 285 s alone, so 720 s cannot
be hiding a hang; and the readiness wait is for a *process to bind a port*, which is not a claim the
product makes.

## Proof

- `harness.test.ts` + `a11y-budgets.test.ts`: 15 tests green after the change.
- `bestpractice.command.test.ts`: 12 tests green, 284.5 s (measured by vitest's own duration line).
- The full suite before the cap: 3 files failed, 94 passed, 1054 tests.
- The full suite after the cap: **97 passed + 3 skipped (100 files), 1057 tests, 61/61 gates, 402 s.**

## Stated limits

- Contention failures can still happen on a slower machine; the numbers are headroom, not a guarantee.
- The remaining deep-audit tests (`bestpractice.file-scope`, `component-states`) keep 420 s: each runs one
  fixture in ~20–50 s, so they are far from the boundary, and widening them without a measurement would be
  the same mistake in the other direction.
