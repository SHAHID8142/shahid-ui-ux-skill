## Acceptance item by item

**1. Pinned by revision with a retrieval note that states what was and was not used.**
`pin.json` records release `v1.0.0`, revision
`4dd968349e54ca45a05dd5c818fb035c9054b022`, Apache-2.0, and four guide paths, with a
measured `sha256` per guide and a parent manifest digest over them (see the amendment
below: this started as `sha256: null` / `unverified` and was measured afterwards).
`verificationNote` names the tool that measured it and what measurement does not
establish, and no guide text is quoted anywhere. The `notPinned` list names the three
things that are *not* covered: the other ~250 guides, the upstream tooling
(search/retrieve/legacy-scan/install), which is pinned nowhere and run nowhere, and
content review. The provider still refuses to emit a hit unless the parent pin and the
guide row are both `verified: "verified"` and the loader's bytes match the digest, so a
record cannot silently become evidence.

**2. The guard is recorded and checkable; telemetry/offline stated, not assumed.**
`checkResponsiveTable({css, markup?})` returns five checks — `pseudo-label-pattern`,
`header-stays-in-a11y-tree`, `overflow-not-concealed`, `cell-labels-complete`,
`label-order-matches-header` — and its 22 tests prove it against the real
`fixtures/admin` pair (pass), against seven mutated copies (each fails a *named*
check), and against both pilot pages. Getting those 22 tests to pass found two real
defects in the guard, fixed in this task:

- `pseudo-label-pattern` only matched `content: attr(data-label)` exactly, so the
  anti-pattern's own `attr(data-label) ': '` decoration read as "no pattern" and
  skipped the header check entirely — the guard would have passed the very page it
  exists to reject. Now any rule that paints the attribute counts.
- A table using neither half of the pattern (no `data-label`, no painted label) was
  reported **fail**; it is out of scope, and it now reports `not-applicable`.

Telemetry and network are stated in `docs/RESEARCH_SOURCES.md` §9 and enforced in
`research-provider.ts`: no analytics, no telemetry, no background calls; the online
arm requires `SUS_RESEARCH_ONLINE=1`, and the offline path returns `available: false`
with `loaderCalls: 0` rather than an error. Caps are constants, not conventions:
`RESEARCH_MAX_QUERY_WORDS` / `MIN`, `MAX_HITS_PER_QUERY`, `MAX_EXCERPT_CHARS`,
`MAX_CALLS_PER_RUN`, and `RESEARCH_SUPPORTED_LICENSE = 'Apache-2.0'`.

**3. At least three pilots with measured before/after.**
Three pairs under `evals/research/modern-web-guidance/pilots/`, driven in Chromium at
390 px through `ariaSnapshot()`, document-overflow, axe serious/critical and
`runHardeningMatrix` (3 viewports x 2 themes x 2 motion):

| Pilot | Instrument | before | after | negative / fallback |
| --- | --- | --- | --- | --- |
| responsive-table | `columnheader` count | **0** | **4** | forced `display:none`: 0; at 320 px: 4 |
| navigation-drawer | contract flags from the snapshot | `aria-expanded` absent, focus not moved, 4 tab steps behind the drawer, Escape does not close, focus not returned, 0 links without JS | all six true/0, `noJsVisibleLinks` 4 | drawer never opens: not-run |
| inp-handler | long tasks on the performance timeline | 1 task, 360 ms max, 310 ms blocking | 0 tasks, 0 ms blocking | timeout fallback: 0 ms blocking |

Every pilot is a `before.html` / `after.html` pair that is served from disk by the
harness, so the numbers are reproducible with `pnpm pilots` and the digests in
`results.json` guard against editing a page after measuring it.

**4. No vendor, no execution, no claim beyond the measurement.**
Nothing from upstream is copied into the repository; `pin.json` quotes no guide text;
the provider is an interface with an injected loader, so no network client, CLI or
runtime is executed there. The one script that does read upstream — `scripts/research/verify-pin.mjs`
— fetches raw file bytes over HTTPS, hashes them, and installs and executes nothing.
`COMPATIBILITY.md` §6 and `pilots/README.md` state the limits inline: headless Chromium
only, `en` locale, synthetic pairs, browser-timeline timings rather than field INP, and
the provider arm is **not-run** because no shipped loader supplies fetched text to a
paired run. A source-text `pass` from the guard never means assistive technology works —
that sentence is in the module header, the receipt and the docs.

## Honest limitations

- **The provider arm is not-run.** The pin is measured (amendment below), so the
  provider *can* serve a hit — but no shipped loader hands fetched text to a paired run,
  so there is still nothing to compare against the *without* half. Issue #14 asks for
  paired tasks with and without a provider; the *without* half is the shipped one, and
  the *with* half is exercised only through an injected fake loader in the provider
  tests. A servable pin is a precondition for that arm, never the arm itself.
- **A digest is not a reading.** Measured bytes prove which bytes exist. Nobody has read
  a guide, so no passage is quoted, §6 stays hypotheses, and no content review has
  happened.
- **Generated content is not nothing.** In the `before` page the 16 cells keep their
  label text in the accessible name, so only the `columnheader` count exposes the
  break. The receipt and the docs say this rather than claiming the labels vanish.
- **The guard is a text heuristic.** It does not resolve the cascade, evaluate media
  queries or observe a browser; it reads the technique. The browser measurement is the
  evidence, the guard is the regression trap.
- Three pilots out of ~254 guides; four guides pinned out of them. Coverage here is
  exactly what was measured, not a fraction of upstream that has been reviewed.

## Amendment 2026-11-16 — the pin was measured, so the record changed

The receipt above was written when `sha256: null` was the honest state. Issue #14's
first acceptance item asks for a compat report that cites the pinned revision *and* is
not merely repeated from triage, and §4 of `docs/RESEARCH_SOURCES.md` says an unverified
pin is a review obligation. So the pin was measured, once, deliberately, and every
sentence that asserted "unverified" moved in the same commit.

**Tool.** `scripts/research/verify-pin.mjs` (new). It fetches the licence and every
pinned guide **twice by different transports** — the raw content host and the GitHub
contents API at the same ref — and refuses to hash anything unless the two answers are
byte-identical. `--write` refuses to replace a digest that is already recorded, so a
refresh cannot quietly absorb moved upstream bytes. It is deliberately **not** in
`pnpm verify`: a build must never need the network, and a gate that failed because
GitHub was unreachable would teach people to skip it.

**Run, observed.**

| Command | Expected | Observed |
| --- | --- | --- |
| `node scripts/research/verify-pin.mjs` (offline) | refuse before fetching | exit 2, `refused: set SUS_RESEARCH_ONLINE=1 to fetch upstream.` |
| `SUS_RESEARCH_ONLINE=1 node scripts/research/verify-pin.mjs` (check) | report the pin is incomplete | exit 1, `[FAIL] the pin is not complete: 4 guide(s) unrecorded, verified="unverified".` |
| `SUS_RESEARCH_ONLINE=1 node scripts/research/verify-pin.mjs --write` | record four digests | exit 0, `[PASS] recorded 4 guide digests, verified="verified"`, parent `86872acde276e316c8e8533db89a64900155852efe25611bd9cf2e8f21e78f72` |
| re-run in check mode after the pin was reviewed by hand | the record still matches | exit 0, `[PASS] every recorded digest matches the fetched bytes.` |

**What the pin now holds.** Per guide: a 64-hex `sha256` and `verified: "verified"`;
plus `licenseSha256` for `LICENSE`, `verifiedAt`, `verifiedBy`, and a `verificationNote`
that states the method and its limits. The parent `sha256` is a **manifest** digest over
`revision`, `licenseSha256` and each guide path + digest in pin order, so a reviewer can
recompute it from the file without a network.

**What this does not establish, and is not claimed.**

- Not that anyone read a guide. No passage is quoted anywhere; §6 of
  `docs/RESEARCH_SOURCES.md` stays hypotheses; the content review in §4 step 4 has not
  happened.
- Not that the advice is correct, or that it overlaps or contradicts a SUS rule.
- Not the with-provider pilot arm. The pin is now servable, but no shipped loader
  supplies fetched text to a paired run, so it stays `not-run`.
- Not a licence decision. `licenseSha256` pins upstream's Apache-2.0 text; D06 stays open.

**Tests added with the change.** `packages/scanners/tests/verify-pin.test.ts` (11 tests)
holds the script's rules without a network: two transports must agree, disagreement
throws instead of picking a winner, a recorded digest is reported as a conflict rather
than a fill, an absent guide is a conflict rather than a silent addition, and the
shipped pin's manifest digest is re-derived from its own rows. The provider test file's
final block was rewritten to assert the pin is a *measured record* — real digests, the
expected manifest, the note's method sentence — and that the provider serves a hit only
when a loader returns the pinned bytes, while a loader returning `'e'.repeat(64)` is
rejected as `no-match` and an unverified pin still spends no lookup.

## Amendment 2026-11-16 — issue #14's supply-chain item, applied to this repository

Issue #14 asks that third-party provenance be verified before anything is installed and
that a version be pinned rather than floated. That argument does not stop at the research
source: `.github/workflows/ci.yml` was still running `actions/checkout@v4` and two more
actions on floating major tags, which means the code executed on every push was whatever
upstream had published most recently — unreviewed by anyone here. All 12 `uses:` lines now
name a 40-character commit with the resolved tag kept beside it
(`actions/checkout` `11d5960a…` v4.4.0, `actions/setup-node` `49933ea5…` v4.4.0,
`pnpm/action-setup` `b906affc…` v4.3.0 — `v4` is an annotated tag there, so the tag object
was dereferenced rather than pinned).

That change is recorded, with the `gh api` resolution and a negative control, in
[CI_ACTIONS_PRIVATE.md](CI_ACTIONS_PRIVATE.md) — the T0103b receipt that owns `ci.yml` —
and it is held by `packages/schemas/tests/ci-actions-pinning.test.ts` (5 tests), which
fails on a tag, a branch, a short SHA, a pin that drifts from the recorded commit, or a
`docker://…:latest`. The pins are a hygiene control: they change nothing CI *runs* and
they do not widen release authority (T1005 stays owner-only, T1006 still verifies the
checkpoint).
