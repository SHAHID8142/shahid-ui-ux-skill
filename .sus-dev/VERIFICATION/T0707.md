## The engineering decision (and why it is the strong one)

The task text suggested `ts-morph`/`recast`. Both are printed-AST rewriters:
they reformat the file they touch. That would break the product's own promise —
the approved diff must be the written diff, and the user's unrelated
uncommitted bytes must survive. So:

**AST for targeting and judgement, bytes for the write.**

- `typescript` (already in the toolchain, now a declared runtime dependency — no
  new supply-chain surface) locates the target JSX element by a stable anchor
  (`id` / `data-sus-id`), and is the judge of validity.
- The write is a **minimal splice**: everything outside the target node's range
  is preserved byte-for-byte. Tests assert the exact resulting source, that the
  edited file gains exactly one line, and that unrelated prefixes/suffixes are
  identical.
- Inserted code is re-indented from the target's own indentation, so generated
  markup matches the file instead of looking pasted-in.

Refusals are the designed path (the task's own rollback rule): invalid JSX
content, a self-closing element that cannot take children without being
rewritten, a replacement that drops the target anchor, an edit that would
duplicate a section anchor (which would make every later edit ambiguous), an
ambiguous or missing anchor, and any post-edit parse failure.

## The apply path, in refusal order

1. **receipt replay** — same operation id returns the stored receipt; no second write
2. **unfinished transaction** — a prepared-but-unapplied manifest blocks new work until `recoverInterrupted()`
3. **approval grant** — content-bound hash + expiry + proposal id (`stale-base`/`expired` → `stale-approval`)
4. **plan coverage** — every planned file approved, every approved file covered, a whole-file delete carries no AST edit
5. **action boundary** — trusted provenance (DA-31) + single-use capability bound to session/frame/kind/proposal hash/fence/TTL
6. **preimage recheck** — current bytes must equal the approved preimage (a race is a conflict, never a merge)
7. **section owner** — AST resolution; ambiguous/missing anchor refuses
8. **durable transaction** — manifest + preimages before the first write (DA-35)
9. **verification** — the project's own typecheck/build; failure reverts exactly
10. **receipt** — durable `.sus/ops/<id>.json`

`ApplyEngine` **refuses to be constructed without a verify function**: an engine
that cannot verify would write changes it cannot vouch for.

Undo is transaction-specific: it restores that transaction's preimages and
refuses (`undo-conflict`) if the file changed after apply. There is no
`git reset`, stash or checkout in the path (a read-only git snapshot — HEAD +
dirty-path count — is recorded in the receipt for correlation only).

## Honest limitations

- **No HTTP route reaches the engine yet.** The bridge server remains a
  read-only session surface; wiring a route is a separate, security-reviewed
  change (recorded in the threat model limitation 1).
- **Verification is only as good as the injected verifier.** The engine requires
  one and records its verdict verbatim; it does not pretend a syntax-only check
  is build verification. Production wiring must pass the consuming project's
  own typecheck/build command.
- **Edits support insert-child/before/after, replace-node, delete-node.** There
  is no multi-file coordinated component extraction (that is T0802/T0700w
  territory), and provenance/mapping still come from the caller.
- **`undo` keeps the transaction's preimages on disk** after a successful apply
  so undo remains possible; retention/pruning of `.sus/transactions` is not
  implemented and is recorded rather than silently ignored.
