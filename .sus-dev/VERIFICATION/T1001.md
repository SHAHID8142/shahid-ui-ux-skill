  pipeline. Acceptance: a single command runs everything in under 10 min, and a
  reachability check proves every non-M10 task is in the ancestry (audit H6).
- **Agent:** pi. **Verdict:** PASS. Real run: 3 stages, **129.8 s**, exit 0.

## The single command

`pnpm regression` (`scripts/regression.mjs`) runs, in order:

| Stage | Command | What it covers |
| --- | --- | --- |
| 1 | `pnpm verify` | handoff, reachability, the gate suite, lint, format, stylelint, typecheck, build, directions, motion, parts, support-matrix drift, all unit tests |
| 2 | `pnpm demo:loop` | the full studio loop end to end on a real Astro build in Chromium |
| 3 | `pnpm dogfood` | the three reference implementations, built and audited (T0906) |

`pnpm verify` itself now begins with `pnpm reach` (below), so reachability is
checked on every verify, not only in the regression run.

The first failing run cost 2.7 s and the report still named the revision; the
suite was kept honest by two real fixes rather than by loosening it: an ESLint
`no-explicit-any` violation in the new tests, and generated reports needing a
`.prettierignore` exemption (they are machine output, like the other generated
artefacts).

## Fail-closed reporting

`scripts/lib/regression.mjs` holds the aggregation rules as pure functions:

- **an empty run is a failure**, not an empty success;
- **a stage that did not run is `not-run`**, and any `not-run` prevents `pass` —
  the gate-registry rule applied to a whole pipeline;
- **the report names the revision and flags a dirty tree**, because a green
  verdict against uncommitted changes describes a different commit;
- stages are recorded as `not-run` rather than dropped when Playwright is absent.

The committed report lives at `evals/reports/regression-latest.md` (+ a
per-revision JSON), so a "complete build" claim has a subject.

## Reachability (audit H6)

`scripts/check-reachability.mjs` (`pnpm reach`) answers one question per finished
non-M10 task: is there something behind the `done` claim? Three kinds of backing
are accepted, strongest first — task id in an ancestry commit message, a tracked
`.sus-dev/VERIFICATION/<id>.md` receipt, the task's own delivered file, or (for
read-only tasks such as T0001) its recorded evidence path. Current state:

```
94/94 finished non-M10 tasks backed
(79 by commit id, 10 by receipt, 4 by delivered files, 1 by recorded evidence; 0 M10 exempt)
```

T0001 was, until this check existed, a `done` claim with no commit id, no receipt
and no files — a planning task whose only artefact is a document it edited. It is
now backed by its recorded evidence path. That is the sort of thing H6 was for,
and it is reported honestly rather than hidden by an exemption list.

14 new tests (7 reachability, 7 regression aggregation) pin the negative cases:
an empty run fails, a `not-run` stage fails the verdict, a done task with no
backing is missing, and a missing Playwright downgrades the end-to-end stages to
`not-run` instead of pretending they ran.

## Honest limitations

- 129.8 s here, on this machine, with warm caches and Chromium already installed.
  A cold CI runner with browser downloads will exceed that; the <10 min acceptance
  is met for the measured configuration, not proven for every configuration.
- The pipeline runs stages **sequentially** and stops at the first failure, so a
  later stage's state is `not-run` rather than wrong. That is deliberate: parallel
  stages would make the timing claim cheaper but the report less truthful.
- Reachability is textual over commit messages. A task could be marked done with a
  commit message mentioning it but the work absent; the unit tests and the
  receipts are what catch that, not this check.
