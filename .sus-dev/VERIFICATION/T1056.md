# T1056 — the gate checker cannot silently stop asserting (audit finding T1003-11)

Date: 2026-11-18 · Agent: zcode-audit · Branch chore/continuation-reconciliation

## What changed

- **`packages/schemas/tests/check-gates-coverage.test.ts` (new)** — the checker's own negative
  control, three layers:
  1. **floor**: the checker prints ≥ one `[PASS]`/`[FAIL]` line per unconditional `report()` call
     site in its source (56 call sites − 7 literal-false failure branches → floor 49; a deletion
     of any always-printing assertion drops the output below the floor);
  2. **canaries**: 29 assertion names pinned in the test, independently of the checker's source,
     each required to appear in a live run's output — deleting or renaming one away is red;
  3. the "13/13 gates implemented and verified" verdict line itself.
- **`scripts/check-gates.mjs`**: M13 (audit-finding fixes, D35) joins M11/M12 in the
  post-checkpoint exclusion of the `ancestry(T1001)` assertion — M13 work started after the
  completed M1–M10 checkpoint and is covered by the release ancestry (T1005); rewriting T1001's
  deps would be a false history.
- **`TASKS.json`**: T1005.deps now includes T1046–T1075 (the audit findings are release-blocking,
  so release approval depends on them — same pattern T1017 established).

## Evidence

- `pnpm -w exec vitest run packages/schemas/tests/check-gates-coverage.test.ts` → **3/3 pass**.
- **Negative control (executed)**: deleting the `report(…, 'G7: horizontal overflow at 320px
  fails', …)` call from `scripts/check-gates.mjs` turns the coverage test red with
  "the checker stopped asserting: G7: horizontal overflow at 320px fails"; restoring returns it
  to 3/3. Before this change, the same deletion left the checker exiting 0 with one fewer line
  and no failure anywhere (the audit's finding).
- `node scripts/check-gates.mjs` → exit 0, 61 `[PASS]` / 0 `[FAIL]`, verdict consistent.
- The canary list excludes the two literal-false guards ('G13 is never waivable', 'registry
  registers semantic prerequisites') — they print only when the registry is wrong, so a green
  run can never carry them; they are covered by the checker's exit code.

## Honest limitation (stated, not hidden)

- A condition weakened **in place** (`report(true, …)` keeping the same name) is not caught by
  output inspection. The bad-fixture discipline lives one level down — every evaluator runs a
  committed good and bad fixture and the evaluators' suites assert the bad ones fail — so a
  weakened checker condition diverges from the evaluator suites it summarises, and the checker's
  structural/negative sections still evaluate the same fixtures in-process (G4/G5/G11/G13
  fail-closedness re-proven on every run).
