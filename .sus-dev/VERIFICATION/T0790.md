## What it does

`runVerificationLoop` runs injected stages in safety order and always returns an
answerable outcome:

| outcome | when | revert |
| --- | --- | --- |
| `preview-failed` | entered with a preview error — nothing was written | never |
| `apply-failed` | the apply stage failed — nothing was written | never |
| `verification-failed` | a hard gate failed and the transaction was intact | exactly once |
| `rollback-blocked` | a hard gate failed but the tree diverged, or the revert itself conflicted | not attempted / failed |
| `accepted` | every gate passed (or only soft gates failed) | never |

**DA-36 is enforced at the decision point, not the call site**: the loop asks
`transactionIntact()` immediately before reverting and only then, and a test
asserts the call order is `intact → revert`. If the tree diverged, the revert is
*not attempted* and the report says the user's edits were left untouched on
purpose — the alternative (a "helpful" revert) would destroy their work.

**Soft gates** are reported in the failure object (with the note that they did
not block acceptance) but never trigger a revert of a completed change.

**Diagnostics are redacted by default** — home paths, bearer tokens, `sk_/pk_/rk_`
keys (including `sk_live_…`), `ghp_` tokens, emails and long digests — while
keeping what a person needs to act (file:line, `TS2322`). A caller-supplied
redactor replaces the default for the whole report. A throwing stage becomes a
redacted failure with a recovery path, never a crashed loop.

## Honest limitations

- The loop orchestrates stages; it does not itself run axe/Lighthouse/motion. The
  production wiring (T0708/T0905) supplies those runners, and until then the
  loop's guarantees are about classification, recovery and the revert decision.
- "Concise explanation" is the first failing stage's summary plus a curated
  recovery list. Deep multi-cause failures still show only the first hard gate,
  intentionally (fixing one thing at a time is what users can act on).
- Latency is not yet bounded by a deadline: a hanging stage hangs the loop. The
  recorded rollback (async verification with a status surface) is the design for
  that, and it is not implemented here.
