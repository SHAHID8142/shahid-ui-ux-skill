# T1043 — the authorized proxy's `CONNECT` handling, probed instead of assumed

**Found by:** answering a peer-review question that had sat in `.sus-dev/INBOX.md` unanswered ("CONNECT
handling for a host with an IPv6 literal, and whether the 403 body leaks anything").
**Branch / base:** `chore/continuation-reconciliation` after `69c8a45`.

## Verdict

**Pass**, after two fixes. Both were fail-closed, so neither was a disclosure; both were misleading.

## What was wrong

1. **An IPv6 target was parsed as `[`.** `req.url.split(':')` reads `[::1]:443` as host `[`, so:
   an authorized IPv6 host could never be reached through a tunnel, and the refusal recorded a host
   (`[`) the operator could not paste back into `--authorize`. Fixed by parsing the target as a URL and
   stripping the brackets a WHATWG `hostname` keeps on an IPv6 literal — the same strip now also applies
   to the plain-HTTP path, where `--authorize ::1` previously could not match `http://[::1]:port`.
2. **A tunnel that could not open was dropped without a response.** The client waited for its own timeout
   instead of being told. Now `HTTP/1.1 502 Bad Gateway` is written before the socket closes, matching what
   the plain-HTTP path already did with its 502.

## About the 403 body

It echoes the host the client itself requested. `packages/eval-core/tests/proxy-connect.test.ts` pins that:
no port, no path, no upstream detail, nothing the caller did not already send.

## Proof

`packages/eval-core/tests/proxy-connect.test.ts` — 4 tests, green:

| Case | Expected | Measured |
| --- | --- | --- |
| `CONNECT unauthorized.invalid:443` | 403, host recorded | 403, `unauthorized.invalid` recorded |
| `CONNECT [::1]:9` (loopback, nothing listening) | 502, not a parse accident | 502; `[` never recorded; `::1` not refused |
| `CONNECT [2001:db8::1]:443` unauthorized | 403 naming the address | 403, `2001:db8::1` recorded |
| `CONNECT :::` malformed | 400 or 403, no hang | 400 |

`net-guard.test.ts` (9 tests) still green, and the redirect/browser-navigation decisions are untouched.

## Stated limits

- Only `CONNECT` and the plain-HTTP host comparison were probed. Other request forms (`OPTIONS *`, an
  absolute URI with credentials) are not covered by these tests.
- The proxy still does not intercept TLS: it constrains which hosts can be reached, not what is inside the
  tunnel. That is stated in the module header and remains true.
