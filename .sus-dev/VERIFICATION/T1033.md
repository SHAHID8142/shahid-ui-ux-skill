# T1033 — a Studio surface you can start, described as what it is (issue #21 R4)

**Task:** issue #21 R4: the README calls the Live Studio mandatory, but nothing documented a way to
start it — `studio-web` is a library, `demo:loop` is a test, and `package.json` had no studio script.
**Approval:** D32 issue triage inside D28; follows the owner's `go ahead` on the R-series.
**Branch / base:** `chore/continuation-reconciliation` at `bcbae54`.

## Verdict

**Pass on the half that exists.** `pnpm studio:bridge` starts the real bridge and is proven end to end;
the Studio *page* still does not exist, and every document now says so instead of implying it.

R4 offered two honest endings — a launcher, or an explicit statement that Studio is a tested vertical
slice. This does **both**, because neither alone is honest: a script named `studio:dev` that starts only
a bridge would imply a UI, and a disclaimer without a runnable surface leaves the bridge untested by
hand.

## What is proven

| Claim | Evidence |
| --- | --- |
| The bridge starts on loopback with an OS-assigned port | `packages/studio-bridge/tests/bridge-launcher.test.ts`, test 1 |
| A valid session token is accepted (`200`, envelope recorded) | test 1 |

## Why the launcher cannot be a second, weaker door

It does not construct its own guards: it instantiates the same `BridgeServer` with the same posture,
and the test asserts the refusals through the started script (401, 403, 400) rather than through the
library, so a launcher that bypassed a guard would fail.

## Stated limits

- No Studio page, no bundler entry, no dev server for the overlay: `@sus/studio-web` remains a
  controller library exercised by tests. That is a build-tooling task, listed in `docs/STUDIO.md`.
- No host browser attach path is verified; `CdpOverlay` exists but no host row reaches a supported tier.
- The token is printed once and lives only as long as the process, matching the bridge's design.
