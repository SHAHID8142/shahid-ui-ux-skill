## Why this exists

T0700 measured static/uninstrumented mapping at 65%/40% and 81%/65% — NO-GO on
both stacks — and named the cause exactly: the unmatched anchors are the
*map instances* (`id={f.id}`, `id={p.id}`), which source parsing cannot see.
The recorded fallback ladder therefore requires a render-time `data-sus-id`
stamp. This module is that stamp plus the index that turns a stamped anchor
back into one owning file.

## What was built

**Stamping** (`stampJsx`, `stampAstro`, `stampSource`)
- Next/TSX: the TypeScript compiler decides what is an element; the stamp is a
  byte-minimal insertion immediately after the element's own `id` attribute.
  Literal ids mirror the literal, expressions mirror the expression **with
  braces preserved** (`data-sus-id={f.id}`).
- Astro: a template scanner, because Astro is not TypeScript. It skips the
  frontmatter, respects quotes and `{}` nesting when finding the end of a tag,
  and never touches a string that merely looks like a tag inside an expression.
- Id-less files are returned **byte-identical**; re-stamping any already
  stamped file is a no-op; unsupported extensions are refused rather than
  half-stamped.

**Owner index** (`buildOwnerIndex`, `resolveOwner`, `resolveStyleOwner`)
- literal anchors → their file and line;
- map instances → resolved through a **same-file array literal**
  (`products: [{id:'teapot-ember'}, …]` + `{products.map((p) => <li id={p.id}>)})
  so `teapot-ember` resolves to the element that renders it;
- a shared component used by many pages has one owner (the component file);
- computed data (`rows: Row[]` from props) is indexed as `?r.id` — unresolved —
  and never guessed;
- style ownership: a `.css` class and an Astro scoped `<style>` class both
  resolve to their file; a class defined in two places refuses.

Refusal reasons: `unknown-owner`, `ambiguous-owner`, both carrying detail and
candidate list so the UI can explain itself instead of failing silently.

## Bugs the tests caught (both real, both fixed)

1. **Expression stamps lost their braces** — `data-sus-id=f.id` is invalid JSX;
   the parse-diagnostics test failed with 12 errors. Caught before any wiring.
2. **Astro map params were not bound to their array** — `id={p.id}` yielded the
   literal anchor `"p.id"`, which would have mapped every product to a
   non-existent element. Also: the param→array scan had to run over the whole
   file, and the brace flag had to come from the regex group rather than a
   `{...}` string test.

## Collateral hardening found on the way

`pnpm verify` failed once with `ENOENT fixtures/commerce/dist/index.html` in two
different suites: `astro build` clears `dist/` while writing, so a build running
next to those suites leaves the artefact absent for a moment. Both suites now
share `tests/support/fixture-html.ts`, which returns the built page and builds
the fixture only when the artefact is genuinely missing — one helper, no
duplicated workaround, and the suites no longer depend on step ordering.

## Honest limitations

- The index resolves map instances only when the data literal is in the **same
  file**; portable datasets (imported JSON, CMS fetches) stay `unknown-owner`
  on purpose. That is a mapping gap, recorded rather than papered over, and it
  is exactly the case T0700w-b must exercise so the verdict is not optimistic.
- The Astro scanner is tag-level, not a full HTML parser: it handles the
  fixture shapes (nested attributes, expressions, `<style>` blocks) and refuses
  nothing it cannot see, but a hand-written attribute containing an unbalanced
  `}` would confuse it. TSX stamping has no such limit.
- Stamping is a source step; wiring it into the fixtures' build pipelines
  (`next.config`, `astro.config`) belongs to T0700w-b/plugin packaging.
