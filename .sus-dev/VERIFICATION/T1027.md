## Why rule-level, not playbook-level

A playbook's rules are the things that can be checked; a playbook is not a checkable unit. The old
sentence counted `search-filters`, `tabs`, `accordion` and `form-input-validation` as covered while
each had one rule exercised and four or five not. The record cannot say that: `measuredRules` and
`gapRules` are counted per rule, and `status` is `not-run` when nothing is measured, `partial` when
some rules are, `measured` only when every rule is.

## Drift control

- `--check` re-renders and compares both files byte for byte, so a hand-edited manifest or a new
  playbook without regeneration fails `pnpm verify`.
- A check naming a rule no playbook declares is a **dangling claim** and fails the check too — the
  exact defect a hand-maintained manifest has.
- Tests prove the discrimination: a check for `tabs.<other-rule>` does not lend `tabs` any measured
  rule; a zero-rule playbook is not called measured; every file on disk appears exactly once.
