## 2. Executive summary and independent verdict

### 2.1 What SUS is (per its own documents)

SUS is specified as a **portable, agent-agnostic, research-driven design-intelligence skill** (Agent Skills format: `SKILL.md` + `references/` + `scripts/` + `evals/`) with a **mandatory SUS Live Studio** — a browser overlay for selecting, drawing, annotating, and writing spatial instructions directly over a consuming project's running page, connected to the agent, with source-mapped dry-run diffs, explicit approval, undo/rollback, and a localhost-only bridge.

Target surfaces (v1, web only): marketing/landing, e-commerce, CRM/dashboard/CMS admin, portfolios (priority order, per D14/D20). Native mobile, desktop, email, print, games/WebGL are explicitly out of scope.

### 2.2 Current state: specification only

- **No product code exists.** README.md:12: "Current state: specification only. No code has been written yet."
- **No tests exist.** TEST_EVIDENCE.md:32-33: "No unit, integration, E2E, a11y, visual, security, or performance tests exist. No baseline scores, no calibration, no benchmark."
- **No gate is implemented.** GATE_REGISTRY.md:15-26 lists G1–G12, every one with status "not implemented"; the registry validator T0159 is pending.
- **Build gate closed.** `BUILD_PERMISSION = false`; unlock keyword `APERIO` not yet received (OWNER_DECISIONS_LOG.md:39-41; TASKS.json meta `build_gate`).
- Task health: 87 tasks; 3 done (T0001–T0003), 2 in review (T0004–T0005), 82 pending (TASKS.json meta; verified at `92f3e5c`).
Excluded from review (not read): `reviews/independent/*` (other agents' review artifacts).
### 2.3 Strengths (genuine, evidenced)

1. **Epistemic contract (D15–D17, E1–E9):** "no templates," learner-not-believer, seven labelled claim kinds (normative/external empirical/expert guidance/observed/prior/preference), challenge protocol, dissent ledger, prediction ledger, calibration as product metric. This is the strongest part of the spec and directly attacks AI slop at its source. (docs/PRD_AMENDMENTS_v1.1.md Part 0.5)
2. **Section-by-section approval with persistent project memory** (`.sus/`, `.sus/PRODUCT.md`, `DESIGN_CONTRACT.md`, `SECTION_STATUS.md`, locks) — the real product differentiator, enforced as code via G2/G11 rather than prompt discipline. (PRD §7; amendments A3, A5; GATE_REGISTRY.md)
3. **Three-tier anti-slop taxonomy** with explicit false-positive concern; only the objective tier blocks; precision/recall to be measured before blocking claims (G10). (PRD §8; PRD_GAP_ANALYSIS.md F4/F28)
4. **Evaluation-first sequencing:** M1.5 evaluation spine (rubric, harness, baselines, calibration) precedes the knowledge library (M2–M4) — quality measurable from day one. (ROADMAP.md; amendments Part 1, A1)
5. **Motion as first-class, mandatory**, with reduced-motion alternatives, interruption tests, and state-machine schema (M6/M6.5). (PRD §9; amendments A6)
6. **Fail-closed security posture by design:** localhost-only bridge, Origin/Host validation, DNS-rebinding guard, no `unsafe-eval`, `data-sensitive` redaction, audit log, recovery manifest, never overwrite uncommitted user work. (amendments §7.1–7.5)
7. **Honesty about limits:** public channel/license undecided; hosts labelled supported/experimental/unsupported; no "bug-free," "supported everywhere," or "superior to Impeccable" claims permitted before benchmarking. (COVERAGE_MATRIX.md §4–5; amendments Part 9)
8. **Process discipline:** micro-task protocol, four-value gate verdicts (`pass/fail/not-run/not-applicable`), fresh-context handoff, separate approval classes (architecture / batch / section / external action / GA), ADRs with reversal triggers. (ROADMAP_AND_TASK_PROTOCOL.md; GATE_REGISTRY.md; ADR_DRAFTS.md)

### 2.4 Critical weaknesses

1. **Everything is proposed, nothing is built.** Six ADRs are "proposed"; amendments v1.1 "awaiting owner approval"; all 12 gates "not implemented"; 82/87 tasks pending. The product is a set of intentions.
2. **The mandatory differentiator is unproven.** Live Studio is "mandatory for GA" (PRD §11, §22) but its core technical assumption — reliable DOM→source mapping on real apps via CDP — has not been validated. The mapping spike (T0700, go/no-go: ≥90% of picked nodes map to a single source node with confidence ≥0.8 on at least one stack) sits at M7, after M1–M6 knowledge work. (ADR-003; amendments A8; RISKS R1; TEST_EVIDENCE §3)
3. **No adapter code for any host.** Agent-agnostic compatibility is claimed (FreePi primary; Codex/Claude Code/Cursor/Copilot/Gemini "experimental until smoke-tested") but zero adapters exist; exact host names/versions are unresolved (PRD_GAP_ANALYSIS.md F11); per-host slash syntax undefined.
4. **Security boundary is designed in prose, not engineered.** Threat mitigations exist only as requirements (amendments §7.5); there is no threat model document, no penetration/review task output, no implemented auth/allowlist/CSP code. T1003 ("Independent security/a11y/licence review") is pending at M10 — too late to shape design.
5. **No measured baselines:** no performance numbers, no accessibility results, no anti-slop precision/recall, no rubric-vs-human calibration. Every quality claim is currently unverifiable. (TEST_EVIDENCE.md:30-35; RISKS R2/R16)
6. **Single-context review.** No subagent tool is available; independent cross-check of the plan is "not-run." (PRD_GAP_ANALYSIS.md §4; TEST_EVIDENCE.md:34; RISKS R11)
7. **Release prerequisites undecided:** license, distribution channel, telemetry/retention policy, benchmark hardware/thresholds. (DECISIONS.md open decisions; D06)

### 2.5 Independent verdict

**CONDITIONALLY PROCEED TO GATED IMPLEMENTATION — DO NOT SHIP, DO NOT CLAIM SUPERIORITY, DO NOT PUBLISH.**

SUS has an unusually strong, honest specification for a planning-stage product. Its architecture thinking is mature (evaluation spine, gates as code, fail-closed Studio, epistemic contract). But it is at **conceptual maturity, not product maturity**: zero code, zero tests, zero implemented gates, an unproven core feature (Studio mapping), and an unverified compatibility story. Implementation may begin only after the owner sends `APERIO`, approves ADR-001…006 and amendments v1.1, and the T0700 mapping spike records a go/no-go. Until T0700 passes, no further M4–M6 investment should be committed.

## 3. Overall architecture evaluation

### 3.1 Proposed architecture (from ADR_DRAFTS.md and PRD §5)

The draft monorepo (pnpm workspaces) comprises:

- `skill/` — portable Agent Skill bundle (SKILL.md + references + scripts + evals), canonical source of truth
- `packages/schemas` — Zod contracts + generated JSON Schema
- `packages/scanners` — deterministic DOM/CSS/AST detector + CLI
- `packages/tokens` — token pipeline (validate/resolve/export; DTCG 2025.10 + internal semantic layer)
- `packages/studio-bridge` — localhost server, auth, CDP attach, session state
- `packages/studio-web` — overlay UI (vanilla TS)
- `packages/adapters` — per-host + per-framework adapters
- `packages/eval-core` — rubric runner, evidence bundles, calibration
- `fixtures/` — 4 self-contained apps (one per surface mode); `evals/` — briefs, baselines, judge protocol

Host adaptation: Agent Skills layout canonical; host-specific entry files generated from templates; `sus doctor` validates frontmatter, name/dir match, ≤1,024-char description, token budget. Triggering lives in the ≤1024-char description; evals test triggering should/should-not sets.

Runtime language: TypeScript (Node ≥ 22 LTS, strict, ESM) everywhere, including the detector (ADR-006; Node 20 EOL acknowledged and corrected per F44).

Writes: syntax-aware AST edits (ts-morph/recast for TS/TSX, Astro compiler for `.astro`, PostCSS for CSS), Prettier normalization, recovery manifest before mutation, snapshot + build + axe + screenshots (3 viewports × 2 themes) + motion trace after write, auto-revert only when the transaction is intact. (amendments §7.1–7.4)

### 3.2 What is sound

- Single source of truth (SKILL.md canonical; generated host entries) prevents host drift — a real failure mode in multi-agent skills.
- Zod as authoring source with generated JSON Schema keeps contracts machine-checkable and versioned ($id + version, migration functions).
- DTCG-aligned tokens with derived exports (CSS custom properties, Tailwind v4 `@theme`, TS constants) — exports are never hand-edited; drift gate G12.
- Fail-closed write path with recovery manifest, base-hash verification, distinct failure outcomes (`preview failed` / `apply failed` / `verification failed` / `rollback blocked` / `accepted`). (amendments §7.4)
- AST writes with "refuse unknown syntax" and automatic revert — addresses R9 (AST corruption).
- Section locks (lease file `.sus/locks/<section>.lock`) address the concurrent-edit conflict (PRD_GAP_ANALYSIS.md F12).

### 3.3 Structural concerns

| Concern | Evidence | Risk if unaddressed |
|---|---|---|

### 3.4 Architecture verdict

The architecture is **thoughtful and appropriately conservative** (zero-install TS, deterministic detector, generated schemas, fail-closed writes), but it is **entirely unvalidated**: no ADR is approved, no prototype exists, and the highest-risk assumption (CDP-based mapping on real apps) is deferred to M7. The "robust and heavy" mandate (D03) is appropriate for a design-quality product but must be balanced against time-to-first-evidence — hence the recommended priority order in §12.

## 6. Severity-ranked loopholes, missing requirements, and technical risks

Each entry: impact, evidence, recommendation, verification criteria. Severity reflects cost if left unresolved before the affected work begins.

### Critical

**C1 — No implementation exists; all quality claims are unverified.**
- Impact: The product cannot be evaluated; 82/87 tasks pending, zero product tests, zero implemented gates. Any statement that SUS "works" is unsupported.
- Evidence: README.md:12 ("specification only. No code has been written yet"); TEST_EVIDENCE.md:4, 32–33; GATE_REGISTRY.md:15–26 (all gates "not implemented"); TASKS.json meta (`82 pending`).
- Recommendation: Proceed only under the micro-task protocol; first batch `T0101 → T0102 → T0103 → T0104 → T0151`; no task starts without user-approved scope.
- Verification: `git status` shows no product code under `packages/`, `skill/`, `adapters/`; test runner smoke passes; agreed runner executes a fixture suite.

**C2 — Live Studio's core assumption (DOM→source mapping) is unproven, yet Studio is mandatory for GA.**
- Impact: If mapping confidence falls below the go/no-go threshold on real apps, the flagship feature is unbuildable as scoped; M4–M6 investment could be stranded.
- Evidence: RISKS.md R1 (impact high / likelihood med); ADR-003 (CDP-attached overlay); amendments A8 (go/no-go: ≥90% of picked nodes → single source node, confidence ≥0.8 on at least one stack); T0700 pending; DEEP_AUDIT_2026-11-13.md §4 (visual pen annotations editing wrong code).
- Recommendation: Run T0700 dual-stack spike (Next.js App Router + Astro) **before** M4–M6 knowledge work; record numeric go/no-go; re-scope Studio (e.g., semver-assisted manual workflow) on no-go.
- Verification: Spike report with per-stack confidence distribution and failure cases; go/no-go recorded in DECISIONS.md.

**C3 — Studio security boundary is specified in prose only.**
- Impact: A localhost bridge with CDP access to arbitrary user pages, accepting drawings/annotations as input, could expose local files, secrets, or execute unintended writes if mitigations (allowlist, Origin validation, redaction, fail-closed) are not engineered and tested.
- Evidence: amendments §7.5 (mitigation list, no threat model); RISKS.md R8 (security hole in Studio bridge); TOOLING_CANDIDATES §2 (CDP/Babel instrumentation); T0806 security test suite pending; no penetration review task output.
- Recommendation: Produce a threat model before T0701–T0707; external security/a11y review (T1003) must precede Studio E2E, not follow it at M10; implement fail-closed tests (inject unauthenticated/cross-origin request → rejected; payload cap enforced; `data-sensitive` redacted).
- Verification: Threat model document; T0806 suite runs; `not-run` never reported as `pass` (GATE_REGISTRY.md:11).

**C4 — Gates are wishes, not enforced checks.**
- Impact: G1–G12 have owning tasks and commands on paper only; CI cannot enforce section order, token-only styling, a11y floor, or detector quality.
- Evidence: GATE_REGISTRY.md:15–26 (status "not implemented" for all 12); T0159 (registry validator; drift fails CI) pending; OWNER_DECISIONS_LOG.md D05 ("approval gates must be real code").
- Recommendation: Implement T0159 and the first executable checks (G1, G2, G3) before any section work; each gate must have a negative fixture proving it fails on deliberately bad input.
- Verification: CI runs a gate check on a bad fixture and returns `fail`; gate verdict enum includes `not-run` never as `pass`.

**C5 — Build gate is closed.**
- Impact: `APERIO` not received; no implementation is authorized. Starting now would violate the owner's standing instruction (D11).
- Evidence: OWNER_DECISIONS_LOG.md:39–41 (`BUILD_PERMISSION = false`); TASKS.json meta (`build_gate: "APERIO not yet received"`); HANDOFF.md (BLOCKED: all implementation tasks).
- Recommendation: Do not create product code until `APERIO` + architecture approval (ADR-001…006) + first-batch approval are recorded.
- Verification: No commits touch `packages/`, `skill/`, or `adapters/` before the gate opens.
### High

**H1 — Multi-agent compatibility is claimed but unverified.**
- Impact: "Install SUS in FreePi / Codex / Cursor" cannot be honored; users face broken installs; support matrix would contain unverified rows (forbidden by gate rules).
- Evidence: COVERAGE_MATRIX.md §4 (FreePi "development host — formal smoke test still required"); T0902/T0903 pending; PRD_GAP_ANALYSIS.md F11 ("Auto Pilot exact product unresolved").
- Recommendation: Execute T0902 (FreePi + one additional host) before any "supported" label; publish machine-readable `compatibility.json` (amendments A9); mark everything else `experimental`/`untested` with test IDs and last-verified dates.

**H2 — Claims protocol unexecuted; "superior to Impeccable" marketing is currently impossible.**
- Impact: Comparative claims without benchmark are marketing fiction and violate R14.
