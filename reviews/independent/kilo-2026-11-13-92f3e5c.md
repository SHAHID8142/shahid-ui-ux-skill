## Executive summary

**Verdict: The planning artefacts are exceptional; the product does not yet exist.**

SUS (Shahid UI UX Skill) is at the end of a thorough planning phase (M0 done/in-review; build gate `APERIO` not yet received). The repository contains **zero implementation code** — no `package.json`, no `SKILL.md`, no `packages/`, `skill/`, `adapters/`, `fixtures/`, or `evals/` directories. Everything described in the PRD, amendments, ADRs, roadmap, and TASKS.json is **planned, not implemented, and not tested** (TEST_EVIDENCE.md:4, 32-33, 63-64).

The documentation is unusually honest, detailed, and self-critical: an explicit build gate, an epistemic contract ("no templates", learner-not-believer), a 12-gate CI-enforced registry, a three-tier anti-slop taxonomy, mandatory section-by-section approval, WCAG 2.2 AA with honest caveats about automated-tool coverage, and a risk register (R1-R18). The deep audit (48 findings, 35 High / 13 Medium) and its reconciliation into PRD_AMENDMENTS_v1.1 Part 13 show real rigor.

**The central risk is scope vs. feasibility.** The owner mandated "the full version — no slimmed MVP" (D02) and "robust and heavy" (D03). The backlog is 87 tasks across 10 milestones, including a portable multi-host Agent Skill, a research/anti-slop engine, semantic tokens, 20+ playbooks, motion state machines, and a mandatory Live Studio with CDP-attached browser overlay, AST source writes, and rollback. The single highest-risk technical bet — DOM→source mapping across Next.js AND Astro (T0700 go/no-go) — is unproven, yet Live Studio is mandatory for GA and gates M7-M8.

**Independent verdict:** Do **not** implement until (a) owner sends `APERIO`, (b) ADR-001…006 are individually approved, (c) T0700 dual-stack mapping spike passes its ≥90%/≥0.8 confidence go/no-go, and (d) the first bounded batch (T0101→T0151) is approved. Treat the project as high-risk until the Studio spike lands; the knowledge product can proceed in parallel but the "mandatory Studio for GA" commitment makes the spike a hard gate, not an option.

## Overall architecture evaluation

### Intended architecture (planned)

Per PRD §5 and ADR-001…006:
- **Portable skill core** — Agent Skills spec layout, `SKILL.md` (≤5k tokens) + `references/`/`scripts/`/`evals/`, name/dir match, ≤1024-char description (ADR-002, PRD_AMENDMENTS Part 8).
- **Core layers** (PRD §5.1): orchestrator, foundations (research, color, type, layout, tokens, a11y, motion, content, SEO), component/section playbooks, rules/reference/evaluation, commands+host adapters, Live Studio runtime, project-local state (`.sus/`).
- **Runtime boundary** (PRD §5.2): Markdown skill = reasoning instructions only; browser/code powers live in separate packages; adapter contracts isolate host protocols.
- **Repo layout** (ADR-001): pnpm workspaces monorepo — `skill/`, `packages/{schemas,scanners,tokens,studio-bridge,studio-web,adapters,eval-core}`, `fixtures/`, `evals/`, `docs/`.
- **Tokens** (ADR-004): DTCG 2025.10 JSON canonical + SUS semantic layer; exports (CSS vars, Tailwind `@theme`, TS constants) are derived outputs.
- **Schemas** (ADR-005): Zod authoring + generated JSON Schema; versioned migrations.
- **Runtime language** (ADR-006): TypeScript/Node ≥22 LTS, strict ESM; no Rust/Go at v1.
- **Studio** (ADR-003): CDP-attached overlay + optional dev-server plugin for `data-sus-id` stamping; Playwright-bundled Chromium default; localhost-only bridge, HMAC tokens, CSP nonce, Zod message validation.
- **Progressive workflow** (PRD §7): page blueprint → one section at a time → explicit approval → implement → verify → accept → next section; `.sus/` project memory.

### Architectural strengths

- Clean separation of reasoning (skill Markdown) from execution (Studio/scanner packages) — reduces context bloat and host lock-in.
- Just-in-time loading + code-enforced precedence resolver (security/a11y → project contract → exceptions → foundations → playbook → trends) prevents silent rule conflicts (PRD §6).
- Fail-closed defaults: ambiguous mapping never edits; localhost-only binding; no arbitrary command execution from annotations; schema validation on every message.
- Evaluation spine (M1.5) placed before knowledge library — measurement before assertion.
- Honest support tiers (supported/experimental/untested) instead of "works everywhere" marketing.

### Architectural concerns

1. **Unproven central bet.** CDP-based DOM→source mapping + AST source writes (ts-morph/recast/Astro compiler/PostCSS) across two stacks is the riskiest item and has no spike result yet. ADR-003 reversal trigger is the T0700 go/no-go (≥90% single-node mapping at confidence ≥0.8 on ≥1 stack). Until that passes, ADR-003, T0701-T0708, and the "mandatory Studio for GA" commitment rest on an assumption.

2. **Framework-agnostic claim vs. write-path reality.** PRD/ADR claim framework agnosticism "by construction," but amendments mandate JSX stamping (`data-sus-id`) and ts-morph/recast edits; Astro, CSS, JSON, and content sources are not one TSX write path. Deep audit F29: mapping a DOM node does not identify whether the correct edit belongs in a shared token, component prop, stylesheet, or content source. No cross-stack write-path feasibility evidence exists yet.

3. **Monorepo + 8 packages + 4 fixtures + eval harness before any product code.** pnpm workspaces is reasonable, but the "full/heavy" mandate means a large surface to build, test, and maintain before any user value ships. M1.5 (evaluation spine) blocks M2, which delays the skill core behind measurement tooling — defensible but slow.

4. **No reference implementation yet.** A10 (3 dogfood sites) is M9, so early design decisions lack real-world pressure-testing.

5. **ADR-006 Node floor corrected to 22 LTS** after deep audit F44 (Node 20 EOL April 2026). Good correction, but runtime pins need a maintenance policy (R18).

## Severity-ranked loopholes, missing requirements, and technical risks

Each entry: impact, evidence, recommendation, verification criteria.

### Critical / High

**H1 — Unproven Studio mapping is the single point of failure for GA.**
- Impact: If DOM→source mapping cannot reach ≥90% single-node at confidence ≥0.8 on either stack, the "mandatory Studio for GA" commitment collapses or forces a late re-scope after months of M4-M6 investment.
- Evidence: ADR-003 reversal trigger (T0700 go/no-go); deep audit F26/F28/F29; TASKS.json T0700 acceptance.
- Recommendation: Treat T0700 as a hard go/no-go before M4-M6 Studio work; define the spike's failure modes (repeated instances, shared components, scoped CSS, server-rendered/hydrated markup) explicitly; do not treat "optional dev plugin degrades gracefully" as a substitute for measured confidence.
- Verification: T0700 spike report committed with numeric confidence distribution and failure cases on both Next.js App Router and Astro.

**H2 — Zero implementation; no tests exist.**
- Impact: All quality claims are on paper. Cannot verify performance, a11y, security, or motion behavior before build approval.
- Evidence: TEST_EVIDENCE.md:4, 32-33, 63-64 ("No SUS product implementation was created"; no unit/integration/E2E/a11y/security/performance tests); no `package.json`.
- Recommendation: Sequence M1/M1.5 to produce runnable tooling before M2; require the first batch to ship a passing CI pipeline on an empty repo.
- Verification: `pnpm install; pnpm -r exec tsc --noEmit; pnpm lint; pnpm typecheck` green; CI skeleton in `.github/workflows/`.

**H3 — Live Studio accessibility deferred to M8 (T0807).**
- Impact: A design/collaboration tool that is itself inaccessible contradicts the product's a11y stance; keyboard drawing and SR annotation descriptions are missing until late.
- Evidence: deep audit F13; Coverage Matrix Studio column for CMS admin marked 🟡; T0807 is the only Studio a11y task.
- Recommendation: Pull Studio overlay a11y (keyboard navigation, focus management, annotation list as DOM panel) into M7 slice, not M8 hardening.
- Verification: Overlay passes axe + full keyboard path before M7.9 demo (T0708).

**H4 — WCAG gate text vs. standard exceptions not yet reflected in task acceptance.**
- Impact: G7/G8/G9 could overblock valid layouts or miss failures if applied without the WCAG exceptions the amendments now cite.
- Evidence: deep audit F16-F20; amendments Part 2 restate gates with exceptions; TASKS.json T0807/T0406 acceptance still references "zero targets below 24" and fixed viewport counts.
- Recommendation: Rewrite T0406/T0807 acceptance to test criteria applicability + exceptions, record project policy (e.g., stricter min target) separately from the standard.
- Verification: Gate failures on deliberately-exceptional fixtures (e.g., inline control, essential target, data table) produce `not-applicable` with reason, not `fail`.

**H5 — Approval/section isolation depends on unbuilt locking.**
- Impact: Two agents/tabs could overwrite the same section; G2 (section order) has no owning enforcement until T0505.
- Evidence: gap analysis F12/F25; TASKS.json T0502 (section locks), T0505 (enforcement test), GATE_REGISTRY G2→T0505.
- Recommendation: Implement section lock file (`.sus/locks/<section>.lock` pid+expiry + lease generation/fencing) before any multi-agent or multi-tab use; test crash and expiry.
- Verification: Concurrent apply to same section rejected; expired worker cannot apply after re-acquire.

**H6 — Security boundary is designed but untested; no external review yet.**
- Impact: A localhost bridge with CDP access and source-write capability is a high-value target; prompt injection via drawings/OCR/screenshots could authorize writes.
- Evidence: Part 7.5 security additions; deep audit F31-F33; T0806 security suite pending; T1003 independent review pending.
- Recommendation: Complete threat model + dedicated security CI job (T0806) before T0702 overlay injection; external security review at T1003 before GA.
- Verification: Rebind/CSRF/dns-rebinding attempts blocked; indirect-injection via drawing text rejected at action boundary; audit log append-only.

**H7 — "Superior to Impeccable" claim protocol depends on benchmark that doesn't exist.**
- Impact: Premature comparative marketing would be unverifiable and damage credibility.
- Evidence: PRD §11.5/§16 L; deep audit F43; amendments Part 9 (protocol + n≥20 + all 4 surface modes + reproducible + raw data).
- Recommendation: Enforce claims-protocol lint (claim-checker in CI, T1004) and hold all comparative claims until T1002 benchmark artifacts committed.
- Verification: No `beats`/`superior`/`faster` claims in docs until benchmark raw data released.

### Medium

**M1 — Contradictions between "no templates" and playbook/banned-defaults could produce dogmatic output.**
- Impact: Agents may suppress valid design (familiar checkout, requested style) to satisfy novelty checks.

**M6 — Host claims for Codex/Claude Code/Cursor/Copilot/etc. are "experimental until verified" but no test environments confirmed.**

- Verification: `compatibility.json` generated; CLI `status` matches data; no unverified rows.

**M7 — Single-agent audit throughout; no independent cross-check completed.**
- Impact: All quality judgments (this review included) come from one context; correlated errors possible.
- Evidence: TEST_EVIDENCE.md:35 ("independent cross-check: not-run"); RISKS R11; gap analysis §4.

- Verification: Separate reviewer signs off on ADRs + first task batch.

## Proposed improvements (with reasoning)

1. **Gate the whole build on T0700 spike.** Do not start M4-M6 Studio implementation until the dual-stack mapping spike commits numeric results. Rationale: it's the highest-risk bet; a no-go should re-scope Studio to variant-preview-only while the knowledge product continues (already the documented rollback).

2. **Add concrete numeric thresholds where the PRD currently uses qualitative language.** Performance budgets (LCP/CLS/INP), anti-slop precision/recall targets, rubric composite pass band for release, token budget per section. Rationale: unfalsifiable requirements cannot be accepted or rejected (gap analysis F1-F6).

3. **Pull Studio overlay accessibility into M7.** Rationale: an inaccessible design tool undermines the product claim; cheaper to build in than retrofit (F13).

4. **Separate "measured check" from "review aid" rigorously.** Judged rubric axis and distinctiveness must never influence CI or acceptance; enforce via claim-checker lint. Rationale: prevents rubric inflation becoming a gate (F15).

5. **Add a `.sus/` schema migration task and release support policy.** Rationale: first upgrade is a trust moment; define migration path + supported-upgrade period before GA (F14/F48).

6. **Encode every named milestone barrier as a task dependency with a test proving premature completion is blocked.** Rationale: the graph previously had unresolved/missing barriers (F37/F38); now encoded but needs a "barrier test" to prove enforcement.

7. **Require explicit motion decision ("none, with reason") per section rather than universal motion.** Rationale: static headings don't need hover/loading/success matrices; avoids compulsory decoration (F6).

8. **Complete the independent cross-check before APERIO.** Rationale: D10/R11; all prior review is single-context.
