## Executive summary and final verdict

**SUS is a substantial specification package, not an implemented skill or application.** Its most defensible differentiation is an auditable design process: contextual research, explicit design decisions, constrained section work, visual evidence, and reversible visual collaboration. Its core architecture separates reasoning instructions from runtime powers and avoids claiming universal host compatibility. These are sound choices.

**Verdict: proceed with owner-approved contract work and bounded feasibility experiments; do not treat the architecture as validated or SUS as installable, supported, secure, accessible, or release-ready.** The complete scope is plausible in principle. Its decisive uncertainties—correct source/edit-owner mapping, enforceable permissions across hosts, trustworthy browser approval, and reliable transactions—have not been demonstrated. No evidence presently supports superiority over another product.

The review identifies **4 High-priority design/process risks and 14 Medium-priority defects or requirement gaps**. High priority means “resolve before the affected capability can safely be considered working,” not “a confirmed exploitable vulnerability exists.” There is no runtime code from which to establish a current security exploit. The highest-priority issues are:

- The task graph allows the first write-capable Studio demo before approval receipts, event replay handling, section fencing, and durable recovery are dependencies.
- The application page and the supposedly trusted, privileged overlay have no specified isolation and approval-authenticity contract.
- Mapping acceptance uses uncalibrated confidence/coverage without a required wrong-target or edit-owner correctness threshold.
- Section-order CI detection is presented as enforcement without defining section ownership or the managed-host boundary.

The absence of implementation is intentional and honestly declared in `README.md:3–13` and `docs/SUS_MASTER_PRD_v1.0.md:4–12`. It is not evidence of a failed build. It does mean that the quality of a document must not be mistaken for demonstrated product quality.

## Overall architecture evaluation

The layer decomposition in `docs/SUS_MASTER_PRD_v1.0.md:71–87` is appropriate: a portable orchestrator, shared foundations, scoped playbooks, deterministic tools, host adapters, Studio runtime, and per-project memory. The explicit statement that Markdown grants no browser or filesystem powers is especially important. ADR-001's proposed modular workspace and ADR-005's schema export strategy are reasonable candidates, subject to their stated approval and feasibility gates (`docs/ADR_DRAFTS.md:20–44,151–169`).

| Boundary | Architectural value | What remains to be proven |
|---|---|---|
| Skill → foundations/playbooks | Progressive loading reduces duplication and context cost | Real loader behavior, trigger precision, precedence resolution, cross-reference consistency, host-specific loading constraints |
| Knowledge → deterministic scanners | Separates contextual judgment from observable defects | Rule-level precision/recall, negative corpus, reproducible classification, evidence freshness |
| Orchestrator → project state | Makes decisions and section status resumable | Canonical representation, migration, conflicting edits, fencing, atomic acceptance across source/tokens/evidence |
| Studio page → bridge | Can connect direct visual intent to bounded source changes | Privileged UI isolation, authenticated approvals, frame/tab binding, capability limits and data-flow enforcement |
| DOM → source → edit owner | Can make visual prompting practical | Repeated instances, CSS/content ownership, shared impact, language coverage, safe abstention and HMR invalidation |
| Bridge → host adapter | Avoids hardcoding one agent vendor | Actual host identity, approval interception, cancellation, long-running requests, install/update/uninstall and versioned smoke evidence |
| Source mutation → verification | Supports reversible, reviewable work | Durable preimages, exactly-once effects, concurrent user edits, crash boundaries, failed rollback UX |

Framework independence must be qualified. HTML/CSS/ARIA knowledge can be portable; source transformation, HMR behavior, browser control and host permissions are stack-specific. An adapter interface does not eliminate that work. Likewise, the project is agent-neutral in intent, but no target host is currently verified.

The most useful improvement is to formalize three independent contracts before broad implementation: a **knowledge/claim contract**, a **managed operation and approval contract**, and a **transaction/evidence contract**. Reuse their identifiers across the skill, bridge, adapter, task records, support matrix and release reports. This reduces conflicting interpretations while preserving the full product scope.

## Requirements completeness and contradictions

The primary requirements cover unusually many important concerns: contextual design judgment, factual copy, semantic tokens, responsive states, reduced-motion equivalence, visual prompting, safe rollback, research provenance and honest marketing. The 12-part playbook schema is a good completeness checklist (`docs/SUS_MASTER_PRD_v1.0.md:158–173`).

The remaining problem is authority and integration, not lack of prose. The baseline calls itself authoritative, amendments are proposed, all ADRs remain proposed, and owner decisions approve selected principles without approving every implementation detail (`docs/PRD_AMENDMENTS_v1.1.md:5–7,463–464`; `docs/ADR_DRAFTS.md:3–5,198–202`; `HANDOFF.md:17–20`). A builder needs an effective, versioned set of approved requirements rather than inference from document recency.

Specific tensions requiring resolution include:

- The start prompt advertises a three-file baseline handoff while the repository's actual build gate and amendments live elsewhere (R05).
- Four gate-result values coexist with a fifth exception “verdict” (R06).
- The durable recovery manifest must precede any mutation, yet the verification pipeline says `apply → snapshot` (R07).
- A mapping spike is supposed to protect investment before M4–M6, while the roadmap explicitly allows knowledge work without that barrier. Either policy can be chosen, but they are different risk decisions (`docs/PRD_AMENDMENTS_v1.1.md:181–185`; `ROADMAP.md:31`; R05).
- “No native binaries” conflicts with default Playwright Chromium as a runtime prerequisite (R15).

Several apparent concerns are already addressed in the current primary contracts and should not be reported as wholly missing. Lessons have a scoped promotion/retirement lifecycle and consent boundary (`docs/PRD_AMENDMENTS_v1.1.md:105–118`). WCAG-related gates record standard exceptions and distinguish automation from conformance (`:207–223`). The gate registry preserves a non-conformance consequence for signed exceptions (`docs/GATE_REGISTRY.md:30–41`), although its result schema is inconsistent. Distinctiveness is excluded from the 11-axis acceptance arithmetic (`docs/PRD_AMENDMENTS_v1.1.md:255–262,278–285`). The regression task does reach all non-release tasks. These strengths do not remove the findings below, but they narrow them.

## Severity-ranked findings

Severity is relative to the intended product. **High** identifies a material safety, correctness or core-workflow risk before the affected implementation is accepted. **Medium** identifies a concrete contradiction, missing contract, misleading validation path or maintainability problem. Design risks are labeled as unverified; they are not security vulnerability claims.

### R01 — High: the first source-writing Studio slice does not require its safety contracts

**Evidence:** T0707 depends only on T0706 and T0503 (`TASKS.json:1276–1295`). T0708's full-loop demo depends on T0707/T0790 (`:1299–1315`). New transitive checks show T0707, T0708 and T0790 all exclude T0502 state/locks, T0504 persistence/fencing, T0508 version-bound approvals, T0709 event lifecycle, T0805 crash recovery, T0806 security tests and T0807 Studio accessibility. Those controls are separately specified at `:901–923,947–974,1436–1503,1957–2002`.

**Impact:** A dependency-following builder can mark an apparently verified source-write demo complete before stale-approval rejection, replay handling, lock fencing and durable recovery are required. Final GA reachability catches task completion later; it does not enforce safe first use or integration.

**Recommendation:** Introduce a minimum safe-write barrier. Split foundational receipt/event/transaction/security/accessibility behavior from later hardening polish, and make the write slice consume their tested outputs. Keep early exploratory writes in disposable fixtures until that barrier passes.

**Verification:** A graph validator rejects write-capable tasks without the required ancestry. The first accepted write demo must reject changed hashes/stale receipts, apply duplicate requests at most once, fence expired workers, preserve concurrent edits, survive interruption at each write step, and provide an operable keyboard path.

### R02 — High: the privileged overlay is trusted by assumption

**Evidence:** ADR-003 injects the overlay into the target application with CDP (`docs/ADR_DRAFTS.md:87–100`). Amendments issue short-lived tokens to a “trusted overlay” (`docs/PRD_AMENDMENTS_v1.1.md:371–384`). The documents do not specify isolation from application JavaScript, token-delivery placement, or which UI/event boundary authenticates a human approval.

**Impact:** The lower-trust page shares a visual environment with controls that can authorize filesystem operations. Host/Origin checks, a nonce and message validation do not, by themselves, establish that the page cannot impersonate those controls. This is a security design gap; no exploit was run or established.

**Recommendation:** Define the trusted approval surface, execution isolation, token channel, frame/tab/session binding and target-page capabilities before implementing privileged operations. Keep the target page unable to mint approvals or obtain general bridge capabilities. Choose the concrete isolation mechanism through a threat-model experiment.

**Verification:** A hostile local fixture attempts token reads, forged bridge messages, synthetic approval events, DOM replacement, cross-frame confusion, navigation/reconnect rebinding and direct privileged calls. None may authorize an operation; real approval must remain scoped to the displayed proposal and source hashes.

### R03 — High: the mapping go/no-go can pass without demonstrating correct edit ownership

**Evidence:** The spike accepts ≥90% single-node mapping at confidence ≥0.8 (`docs/PRD_AMENDMENTS_v1.1.md:181–185`; `TASKS.json:1121–1138`). The mapping contract explicitly calls 1.0/0.6/0.3 evidence tiers, not calibrated confidence, and acknowledges repeated-instance ownership ambiguity (`docs/PRD_AMENDMENTS_v1.1.md:335–342`). Wrong-target and abstention rates are tracked, but no required wrong-owner ceiling or denominator is specified.

**Impact:** Stamping many nodes can satisfy the stated coverage/tier target while still selecting a shared component, content record or CSS rule whose mutation affects the wrong instance or multiple sections. DOM identity is not edit permission.

**Recommendation:** Measure separately: selectable-node coverage, exact target correctness, instance/data/style owner correctness, shared-impact detection, abstention and effort. Use labeled ground truth. Define allowed auto-apply cases and required refusal cases; do not turn the tier number into a probability.

**Verification:** Pre-register acceptance thresholds and unsupported classes before the spike. Held-out cases must include repeated/conditional components, shared tokens/CSS, portals, Astro templates, TSX and content files. Any sampled wrong-owner write must fail the applicable auto-apply safety test; unknown cases must abstain rather than guess.

### R04 — High: section enforcement lacks an ownership model and a stated host boundary

**Evidence:** G2 says section N+1 code being present before N is accepted should fail (`docs/PRD_AMENDMENTS_v1.1.md:215–216`); the registry instead compares status with changed files (`docs/GATE_REGISTRY.md:16`). T0505 tests out-of-order edits and shared-impact reopening, without defining the source-to-section ownership relation (`TASKS.json:981–1003`). The PRD correctly states that Markdown instructions have no direct runtime powers (`docs/SUS_MASTER_PRD_v1.0.md:85–87`).

**Impact:** Existing sites already contain later sections. One route file can own several sections; one component or token can affect many pages. File-level checks can both block legitimate edits and miss unapproved section changes. CI normally detects changes after they have occurred; it cannot promise interception of arbitrary host filesystem tools.

**Recommendation:** Define stable section/component IDs, a change-impact graph, existing-site onboarding, shared-resource policy, and receipt-scoped allowed changes. Distinguish prevention inside managed Studio/adapter operations from post-edit detection in CI. Hosts lacking an enforceable write boundary must publish that limitation.

**Verification:** Fixtures cover an existing four-section page, multiple sections in one file, shared components/tokens, nested sections, route changes and direct host-tool edits. Approved changes pass; unapproved managed operations are prevented; bypassed edits are detected and cannot produce an accepted record. Reports identify which guarantee each host actually supports.

### R05 — Medium: the advertised bootstrap does not load the effective current authorities

**Evidence:** The portable prompt requires only the original PRD, task protocol and audit companion (`docs/AGENT_START_PROMPT.md:3–9,23–28`). It omits amendments, owner decisions and current task records from the mandatory first read, and contains no `APERIO` gate. Current authorities place that gate at `docs/OWNER_DECISIONS_LOG.md:36–44`, while ADR/amendment approvals remain pending. Spike timing also differs between amendments `:181–185` and `ROADMAP.md:31`.

**Impact:** A fresh host following the advertised copy/paste path can re-plan an obsolete backlog, miss the current build restriction, or silently interpret proposed amendments as approved. File existence is not an authority resolver.

**Recommendation:** Bootstrap from one versioned current-state manifest listing required files, precedence, approval receipts, protocol regime and current task graph. Treat the archive as historical. Make the spike-investment policy an explicit owner decision rather than an accidental document-order choice.

**Verification:** A clean-session fixture using only the advertised instructions must identify missing authorities, report the correct build gate, separate approved requirements from proposals and resume the current graph. Generic batch approval must not satisfy an unrelated recorded unlock requirement.

### R06 — Medium: gate results mix check outcome with acceptance disposition

**Evidence:** `docs/GATE_REGISTRY.md:10–11,48–49` requires exactly `pass/fail/not-run/not-applicable`; T0159 repeats this (`TASKS.json:2073–2076`). The same registry requires a `non-conformant-accepted` verdict for exceptions (`docs/GATE_REGISTRY.md:30–35`).

**Impact:** A validator honoring the four-value schema rejects a result another rule requires, or adapters implement different enums. Exception acceptance can also obscure the underlying failed check.

**Recommendation:** Keep `check_verdict` separate from `acceptance_disposition`. Retain the failure, criterion, approver, receipt, expiry and prohibited claims. Define safety/authorization guarantees that cannot be overridden by a design exception. The registry already blocks AA/GA claims for non-conformance; preserve that consequence rather than treating the policy as absent.

**Verification:** Passing, failed, untested, inapplicable, waived-budget and non-conformant-accepted fixtures all validate consistently. An exception never changes `fail` into `pass`; expired exceptions and unsupported enum values fail. Conformance reporting remains separate from product-owner risk acceptance.

### R07 — Medium: preview, recovery and CSP contracts still conflict

**Evidence:** ADR-003 says CDP means “no CSP fight” and previews write candidates to disk (`docs/ADR_DRAFTS.md:90–100`). Amendments require separate generate/preview/apply authorizations and isolated or precisely scoped preview workspaces (`docs/PRD_AMENDMENTS_v1.1.md:360–375`). The durable manifest must exist before any mutation (`:344–352`), but the verification path says `apply → snapshot` (`:364–365`).

**Impact:** Preview workspace ownership is not explicit in the ADR. The later “snapshot” could mean a separate post-apply capture, but the sequence does not say so. The earlier pre-mutation recovery rule is clear and correct; ambiguous terminology can still lead implementations to disagree about what state is durable and recoverable. CSP compatibility remains unverified.

**Recommendation:** Specify one transaction state machine: authenticate scope and freshness → persist durable preimages/manifest → authorized preview/apply → verify → accept or transaction-scoped revert. Define exactly which worktree, server and browser show each candidate, and explicitly supersede stale ADR wording.

**Verification:** Reject/discard, HMR failure, disconnect, CSP/Trusted Types restrictions and termination after every step preserve preexisting tracked/untracked bytes, file modes and index state. Concurrent edits block automatic rollback rather than being overwritten. No policy weakening or source write is implied by merely generating a proposal.

### R08 — Medium: the four-fixture baseline can run before three fixtures exist

**Evidence:** T0153 requires baseline bundles for four surfaces but depends only on T0151/T0152/T0152b/T0154 (`TASKS.json:315–329`). Its ancestry excludes T0102b, which produces fixture apps B/C/D (`:1821–1836`).

**Impact:** The scheduler can unlock an impossible baseline task with only fixture A available, encouraging partial evidence or out-of-scope fixture work.

**Recommendation:** Make the four-fixture producer a prerequisite, or split one-fixture harness calibration from the complete baseline run. Depend on validated fixture artifacts, not only milestone labels.

**Verification:** A scheduling fixture keeps the complete baseline blocked until all four build/smoke outputs exist. Missing or failed fixture evidence cannot be represented as a four-surface baseline pass.

### R09 — Medium: published support status lacks an explicit artifact-to-evidence binding

**Evidence:** T0902 promises install/load/invoke/uninstall smoke tests but does not depend on installer T0904 (`TASKS.json:1528–1547,1573–1593`). T0905's support matrix depends only on T0902, excluding T0903's additional adapters and T0904 (`:1596–1615`). Implementing a generator before later adapters is legitimate; that missing ancestry is not independently a defect. A9 records versions and verification dates, but no explicit artifact-version invalidation rule (`docs/PRD_AMENDMENTS_v1.1.md:190–193`).

**Impact:** A generated matrix can accurately reproduce stale data unless publication is bound to tested artifacts. Smoke evidence may describe manual setup rather than the distributed installer, or a different adapter version. The gap is the claim-publication contract, not the order in which the generator is implemented.

**Recommendation:** Key smoke evidence to the installer/adapter artifact hashes, exact host identity/version, framework, browser and OS. Derive support from matching, successful evidence and a defined support policy; introduce host capability discovery before the bridge contract is frozen.

**Verification:** Changing installer or adapter artifacts invalidates the corresponding support evidence and downgrades the affected row until rerun. Clean global/project installation, invocation, missing capabilities, update, rollback and user-file-preserving uninstall are tested through the shipped path.

### R10 — Medium: gate ownership is inconsistent across the two supposed authorities

**Evidence:** G9's registered owners are T0406 and T0807 (`docs/GATE_REGISTRY.md:23`). T0402 also declares that it emits G9 (`TASKS.json:702–704`); T0807 only declares G7/G8 (`:1493–1495`). T0159 is intended to reject this drift.

**Impact:** Developers can duplicate a semantics check, omit an expected owner or build a validator that compares only one direction. The future executable registry begins with inconsistent input.

**Recommendation:** Use one structured registry for metric producers, check implementations, manual evidence and verdict aggregation. Generate task/document ownership references, and distinguish supporting measurements from the authoritative check.

**Verification:** Compare exact ownership sets in both directions. Missing, extra and duplicate owners fail. The current G9 mismatch must be a negative fixture rather than silently normalized.

### R11 — Medium: the WBS contains parent deliverables presented as executable micro-tasks

**Evidence:** The protocol asks for 15–60-minute reviewable units and explicit results/review fields (`docs/SUS_MASTER_PRD_v1.0.md:418–426`; `docs/ROADMAP_AND_TASK_PROTOCOL.md:83–104`). T0707 bundles AST edits, snapshotting, verification, revert and conflicts (`TASKS.json:1276–1295`); T0805 combines session persistence and multi-file crash recovery (`:1436–1455`); T0811 bundles eight playbooks (`:2099–2118`). All 88 compact records omit the explicit owner/results/independent-review fields. T0104 plans a compact schema, but it does not exist yet (`:220–236`).

**Impact:** Task count understates work and review surface. Broad scopes invite partially complete “done” records, overlapping writers and unbounded verification. Compaction is reasonable only if a schema preserves the completion evidence elsewhere.

**Recommendation:** Retain these IDs as parent outcomes; decompose the next approved batch into child tasks with one observable behavior, bounded paths, realistic effort, one negative acceptance case and an evidence/review receipt. Do not add duplicate state files merely to restore field names: define aliases/references explicitly.

**Verification:** A parent cannot complete while any required child or evidence receipt is missing. A `done` child requires actual command/result or a justified non-executable check, reviewer status, approval scope and rollback outcome. The first approved batch can be reviewed as independent bounded diffs.

### R12 — Medium: the current research synthesis does not meet its own claim-level standard

**Evidence:** The synthesis moves from expert-design observations to broad causal claims about agent expertise and mandatory workflow (`docs/RESEARCH_AND_EXPERTISE_MODEL.md:14–24,28–41`). Lines 19–21 correctly label the agent-expertise corollary `[inference]`; classification is not wholly absent. The concern is the strength and applicability of mechanisms imposed from that inference. Its “verified public behaviour” block attributes `evals/evals.json` to the Agent Skills specification (`:73–85`). The current official specification requires `SKILL.md`, permits additional directories, and does not mandate that evaluation file. [Agent Skills specification](https://agentskills.io/specification).

**Impact:** Informative practice, competitor behavior and inference can be promoted into universal format or design rules. This undermines the project's distinguishing promise of evidence-based disagreement. Schema validity alone also cannot prove that a citation genuinely supports a claim.

**Recommendation:** Apply T0301's intended claim-to-passage mapping to the synthesis itself. Record source version/date, supported passage, classification, applicability, uncertainty and conflicts of interest. Label proposed causal mechanisms as hypotheses until evaluated. Separate standards validation from SUS's own stricter packaging policy.

**Verification:** A valid standards-compliant skill without `evals/evals.json` passes standards validation while SUS policy may separately flag a missing evaluation artifact. Sampled research claims must be supported by inspected source passages; unreachable/contradictory sources become `unverified` rather than fabricated support. This review did not independently verify every article or paper in the bibliography.

### R13 — Medium: prediction hit-rate can measure easy assertions instead of design calibration

**Evidence:** E8 permits self-selected predictions such as headline line count; E9 tracks prediction hit-rate and rubric agreement (`docs/PRD_AMENDMENTS_v1.1.md:105–123`). T0506 governs lesson lifecycle but does not define prediction difficulty, selection bias or a probabilistic calibration protocol (`TASKS.json:1932–1954`).

**Impact:** A system can achieve a high hit-rate through easy implementation assertions while making unreliable usability or conversion judgments. Passing deterministic layout checks does not establish calibrated product expertise.

**Recommendation:** Separate deterministic acceptance assertions from uncertain design/outcome predictions. Record category, pre-observation confidence, baseline, risk and observation method. Include fixed held-out questions alongside author-selected predictions; qualify observational confounding before promoting lessons.

**Verification:** Reports separate categories and include incorrect high-confidence predictions. Easy layout assertions cannot inflate the uncertain-judgment metric. Under matched conditions, compare SUS with a no-skill baseline and report sample size and uncertainty rather than one unqualified hit-rate.

### R14 — Medium: sensitive capture defaults are still undefined for the intended admin use cases

**Evidence:** Studio captures DOM excerpts and screenshot crops (`docs/SUS_MASTER_PRD_v1.0.md:316`). Retention/deletion remain to be defined (`:330`; `README.md:79`). The proposed redaction covers inputs, passwords and marked sensitive nodes, while the data-flow includes remote providers (`docs/PRD_AMENDMENTS_v1.1.md:377–384`). No default treatment of ordinary, unmarked customer text in CRM/CMS tables is specified.

**Impact:** The lower-trust capture surface can contain confidential display text outside form fields. “Local bridge” and password redaction do not establish permission to send that text to a remote model or retain it in artifacts. This is an unresolved policy/design risk, not an observed leak.

**Recommendation:** Decide default capture scope, outbound destinations, artifact preview, allow/deny redaction behavior, retention duration, export and deletion semantics before using real projects. Bind data permissions to the same operation context as source-edit approval; keep project lessons local unless sharing is explicitly approved.

**Verification:** A synthetic CRM fixture contains unmarked customer data, marked sensitive nodes, screenshots and logs. Tests demonstrate the chosen default before any outbound call. Revocation/deletion covers captures, previews, evidence, logs and exported lessons, with documented exceptions rather than invisible copies.

### R15 — Medium: the simple-install promise omits the browser acquisition boundary

**Evidence:** ADR-006 requires `npx` execution without native binaries (`docs/ADR_DRAFTS.md:175–176`); ADR-003 defaults to bundled Playwright Chromium (`:87–89`). Playwright requires version-specific browser binaries and may require system dependencies. [Playwright browser documentation](https://playwright.dev/docs/browsers).

**Impact:** A clean machine or offline environment can satisfy the Node requirement and still be unable to launch Studio. Browser download size, permissions, proxy handling, cache ownership and supported OS combinations are missing from the advertised installation contract.

**Recommendation:** Clarify whether the promise means “no SUS-owned native compilation toolchain.” Specify browser provisioning or compatible existing-browser requirements in installation/status/doctor; obtain applicable download/install permission. Keep the non-default profile requirement for Chrome attachment: that restriction is supported by Chrome's published documentation. [Chrome remote-debugging changes](https://developer.chrome.com/blog/remote-debugging-port).

**Verification:** Test clean supported machines with no browser cache, offline mode, read-only installation directories and interrupted downloads. Doctor reports actionable prerequisites; uninstall preserves unrelated browser profiles/caches and user files.

### R16 — Medium: full Read-surface coverage lacks an explicit long-form evaluation scenario

**Evidence:** Docs/blog/help have full build/redesign/audit targets (`docs/COVERAGE_MATRIX.md:18`). The four-app corpus uses marketing, commerce, admin and a portfolio combining Experience/Read (`docs/PRD_AMENDMENTS_v1.1.md:131–135`; `TASKS.json:1821–1836`). Article layout is second wave (`TASKS.json:2027–2048`); no explicit representative long-form help/docs route is required by the corpus acceptance.

**Impact:** A portfolio can pass while long headings, code blocks, anchor links, content search, document navigation and long-page performance remain untested. Four applications do not automatically exercise all four surface modes meaningfully.

**Recommendation:** Add a representative Read route/scenario inside an existing app, or qualify support until equivalent evidence exists. A fifth app is unnecessary if the current corpus can cover the behavior.

**Verification:** A long-form scenario passes heading/anchor navigation, keyboard reading order, code/table reflow, zoom, localization, content findability and performance checks. Read-specific results are reported separately from portfolio aesthetics.

### R17 — Medium: the mapping task's NO-GO fallback silently removes mandatory Studio behavior

**Evidence:** T0700's rollback says “no-go → Studio re-scoped to variant-preview-only, knowledge product continues” (`TASKS.json:1134`). ADR-003 instead defines three fallback paths that retain draw → intent → diff → approve → apply → undo, with owner re-scope only after all fail (`docs/ADR_DRAFTS.md:109–116`). Full GA still requires Studio spatial editing, recovery and rollback (PRD `:478–480`).

**Impact:** A task runner following its local rollback field can cut the write/undo workflow while believing it followed the plan. An internal preview experiment can be useful, but it is not the specified full product and cannot silently become the fallback scope.

**Recommendation:** Align the task's NO-GO result with the explicit fallback ladder and owner decision checkpoint. Mark preview-only work as an internal experiment with unmet mandatory capabilities, rather than a substitute completion path.

**Verification:** A failed spike cannot advance as a completed Studio or satisfy GA. Each fallback retains its declared apply/undo behavior, and exhausting the ladder produces a blocked scope decision requiring explicit owner disposition.

### R18 — Medium: the evaluation-first barrier does not cover the knowledge/scanner branches

**Evidence:** M1.5 explicitly precedes the knowledge library and M2 (`docs/PRD_AMENDMENTS_v1.1.md:127–135`). T0201 does depend on T0155, but T0301 depends only on T0104 and the scanner chain follows it (`TASKS.json:529–654`). T0401 similarly depends only on T0104 (`:668–689`). Direct ancestry checks show that T0301/T0305/T0401 do not require T0153 baselines or T0155 calibration. Release ancestry alone does not impose this earlier barrier.

**Impact:** A valid graph traversal can build the evidence/scanner/token branches before the measurement spine intended to grade them exists. This contradicts the promised sequencing and can produce fixtures or thresholds fitted to already-written modules.

**Recommendation:** Define explicit milestone-exit artifacts or narrowly scoped measurement prerequisites for affected branches. If foundational schema/token exploration is intentionally allowed earlier, name that exception and keep production knowledge/rule acceptance behind the measurement barrier. Do not force unrelated discovery into a blanket dependency merely to satisfy milestone numbering.

**Verification:** Graph tests demonstrate which production knowledge/scanner tasks wait for validated baseline/calibration artifacts, and which explicitly authorized discovery tasks may run earlier. Negative scheduling fixtures reject premature production-rule acceptance; documentation and dependency policy agree.

## Design, motion and product-quality recommendations

The following are development directions within the existing scope, not claims that a missing runtime currently malfunctions.

**Protect the anti-slop distinction.** Require rule IDs, applicable context, legitimate uses and negative examples. A familiar grid, gradient or checkout layout is not a defect merely because it is frequent. Evaluate objective rules independently from contextual opinions; require precision/recall per rule and surface before blocking. For research-assisted recommendations, test citation support and applicability rather than URL presence alone.

**Keep reuse compatible with the no-template rule.** The intent to avoid filling a brief into canned looks is coherent. Clarify that reusing a consuming project's approved components, semantic tokens and established accessible interaction patterns is allowed. The current “exemplars never as assets” wording and “no templates ever” label need an explicit boundary so agents do not reinvent every component (`docs/PRD_AMENDMENTS_v1.1.md:43–50`; PRD `:23,173,350–360`). Owner selection of a familiar style remains a legitimate preference.

**Judge complete user tasks as well as sections.** The new flow-map foundation is useful (`TASKS.json:2144–2161`). Acceptance should include complete commerce, admin and reading scenarios when relevant: discover → act → validate → recover → succeed. Record real usability checks as `not-run` when absent; a heuristic walkthrough is not user research. Compare quality gains with elapsed time, tokens, number of user approvals/corrections and abandonment. R3 already names a >2× baseline escalation trigger (`RISKS.md:9`); connect it to a measured experiment rather than an automatic quality claim.

**Make purposeful absence of animation explicit.** Motion intelligence should mean an evaluated interaction decision, including “none, because…” where appropriate. Keep meaningful feedback, focus continuity, interruption/cancellation, stale async responses and reduced-motion equivalence mandatory. Independently authored behavior tests must challenge the generated state-machine tests: a wrong schema can generate tests that agree with itself. Include rapid submit, escape during exit, navigation/unmount, slow requests, repeated toggles, touch/no-hover and information parity. The primary requirements already name many of these cases (PRD `:257–285`).

**Separate product accessibility from Studio accessibility.** Both need criteria-to-evidence mapping, including manual/assistive-technology evidence and untested criteria. An overlay can obstruct focus or alter the page's accessible tree; test the app with Studio attached and detached. Automated severity alone cannot establish AA conformance. WCAG's conformance requirements apply to complete pages and processes, so section acceptance is only intermediate evidence. [WCAG 2.2 conformance requirements](https://www.w3.org/TR/WCAG22/#conformance-reqs).

**Budget the validation matrix.** Three viewports × two themes is six screenshots before locales, edge states, motion preferences, browser engines or variants are considered. A1/A7 applicability rules appropriately exempt deliberate single-theme products. Define a fast per-change tier and a complete integration/release tier without weakening mandatory acceptance evidence. Record fixed fixture data/fonts/time, browser versions, repetitions, warm/cold conditions, cache identity, flakiness and retention. Preserve the distinction between lab metrics and field evidence. T1001's <10-minute target is unmeasured (`TASKS.json:1710–1718`); do not guarantee that broad matrix runtime before profiling.

**Tie maintenance to release artifacts.** The planned maintenance owner/review calendar is useful (T1004). Add an approved supported-version policy for schemas, hosts and framework adapters; revocation behavior for stale compatibility evidence; artifact provenance/checksums; dependency/license verification; and a documented security-reporting path before public distribution. Tool “Adopt” rows are candidates, not installed or verified dependencies (`docs/TOOLING_CANDIDATES.md:3–5,71–73`).

The official Impeccable Live page currently documents selection/strokes, variation comparison, source acceptance/discard and session recovery, and labels Live beta. This was verified from its public documentation, not by running it. SUS should benchmark matched workflows and failure cases against a pinned competitor version; its research synthesis's alpha description should be dated historical context rather than a current fact. No performance or quality comparison was run. [Impeccable Live documentation](https://impeccable.style/docs/live/).

## Product-owner decisions required

1. **Effective authority:** Which amendments/ADRs are approved, and what exact combination of unlock, architecture approval and batch approval authorizes implementation? Keep historical statements distinct from current receipts.
2. **Enforcement promise:** Must SUS prevent arbitrary host edits, or guarantee prevention within managed operations plus CI detection elsewhere? Which host capabilities are mandatory for each tier?

5. **Feasibility ordering:** Does the dual-stack spike gate expensive knowledge/workflow investment, or is parallel investment intentionally accepted?
6. **Exceptions:** Which project policies are waivable, which product safety guarantees are not, and what continued-work/AA/GA claims remain prohibited after risk acceptance?
7. **Capture and sharing:** What is the default for unmarked CRM/customer text, provider transmission, retention/deletion, session recovery and cross-project lesson publication?
